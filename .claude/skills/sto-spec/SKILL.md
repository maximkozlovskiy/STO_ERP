# sto-spec — специфікація агрегату і тести, що її стережуть

Один вхід для роботи зі специфікацією: дос'є, BR-ID, аспектні спеки, реєстр, гейти.

## Перед початком

1. `MemoryManual.md` — поточний стан
2. `docs/objects/<entity>.md` — дос'є агрегату, який чіпаємо
3. `.claude/skills/sto-dev/SKILL.md`, секція «Спек-файли: один аспект = один файл»

Таблиця агрегат → дос'є — у `CLAUDE.md`, секція «Крок 3».

## Модель, якої дотримуємось

| Рівень         | Де живе                                                 | Хто стереже          |
| -------------- | ------------------------------------------------------- | -------------------- |
| Бізнес-правило | `docs/objects/<e>.md`, секція «Бізнес-правила (BR-XXX)» | BR-ID                |
| Аспект         | `<module>.<аспект>.spec.ts`                             | реєстр у дос'є       |
| Кейс           | `it(...)` у аспектному файлі                            | `test-baseline.json` |

**1 аспект = 1 файл**, не 1 правило = 1 файл. Обґрунтування виміром: правка
`transition` зараз торкається 3 файлів; при правилі-на-файл торкалася б 8–10, і
DI-обв'язка (~35 рядків) переважила б асерти.

## Сценарій 1 — нове бізнес-правило

1. Дописати рядок у секцію «Бізнес-правила (BR-XXX)» з наступним вільним номером.
   Префікси вже зайняті: `BR-INV`, `BR-SDOC`, `BR-PAY`, `BR-LOY`, `BR-CP`,
   `BR-SUPPAY`, `BR-WORK`, `BR-GOOD`, `BR-WO`, `BR-PO`, `BR-MAINT`, `BR-CAL`.
2. Тест — у **аспектний** файл, що відповідає правилу. Якщо аспекту ще немає —
   новий файл `<module>.<аспект>.spec.ts`, а не `it()` у найбільший спек.
3. Оновити реєстр: рядок у таблиці + число кейсів.
4. Гейти (нижче).

## Сценарій 2 — розбити моноліт

Ознака: гейт B називає файл (>900 рядків і ≥2 top-level `describe`).

```bash
python scripts/check-spec-registry.py --gate-size
```

**Порядок, перевірений на 8 модулях:**

1. `ls <dir>/*.spec.ts` — **фактом, не пам'яттю**. Колізія імені вже знищила
   593-рядковий `purchase-orders.contract.spec.ts`; врятувала випадковість.
2. Межі блоків зсувати назад через коментарі: автор ставить заголовок наступного
   блоку ПІСЛЯ закриття попереднього. Інакше коментар осиротіє в чужому файлі.
3. `describe` переїжджають **дослівно** — тоді `fullName` стабільний і порівняння
   множин працює.
4. Спільний сетап → `<module>.spec-fixture.ts`, **копіюванням з оригіналу**, не
   переписуванням з пам'яті (так загубився `sameCurrency` — 4 тести впали).
   Деструктуризація у ТІ САМІ імена, що були у `beforeEach`, інакше правиться кожен `it()`.
5. Докази — обидва, бо кожен сліпий до свого:

```bash
# кейси: множини fullName проти baseline
cd apps/api && npx vitest run --reporter=json --outputFile=.vitest-report.json
python ../../scripts/check-spec-registry.py --from-report apps/api/.vitest-report.json

# якщо вкладені describe піднімались на top-level — fullName ЗМІНЮЄТЬСЯ законно,
# тоді порівнювати MULTISET листкових it()-назв зі старим файлом

# порядок виконання не впливає (ловить спільний стан у фікстурі)
npx vitest run src/modules/<mod>/ --sequence.shuffle
```

6. **Коментарі перевіряти ОКРЕМО** — множини `fullName` до них сліпі. Порівняти
   нормалізований текст усіх comment-рядків старого файлу проти об'єднання нових.
   Так знайшлися втрати у 5 із 8 модулів, яких тести не бачили.

## Сценарій 3 — аудит покриття

```bash
python scripts/check-spec-registry.py --gate-registry   # файли з реєстрів існують
```

Для кожного BR — чи є тест. Якщо ні, одне з двох: або написати, або записати у
блок **«Чого тут НЕМА»** як свідому прогалину. Мовчазна відсутність — ні.

## Гейти

| Гейт | Що ловить                                     | Команда                |
| ---- | --------------------------------------------- | ---------------------- |
| A    | зниклий/новий кейс проти `test-baseline.json` | `--from-report <звіт>` |
| B    | новий моноліт (>900 рядків і ≥2 describe)     | `--gate-size`          |
| C    | файл або маршрут із дос'є не існує            | `--gate-registry`      |

Baseline оновлюється лише скриптом:

```bash
python scripts/spec-baseline.py apps/api/.vitest-report.json --out apps/api/test-baseline.json
```

Руками не правити: diff мусить показувати РІВНО ті кейси, що змінились.

## Що запускати після правки

```bash
python scripts/affected-tests.py            # робоче дерево; діапазон: --base <sha>
```

Друкує готові команди API / WEB / E2E для зачепленого коду і каже, коли потрібен повний
прогін (спільні пакети, `common/`, конфіги). Unit вибирає граф імпортів (`vitest related`),
E2E — маршрут. Для api-модуля маршрути — це ОБ'ЄДНАННЯ: рядок `**Маршрути UI:**` у дос'є
(одразу під `**Модуль:**`) + однойменна сторінка + сторінки з URL контролерів у web-коді.
Окремо у вибір ідуть спеки, які самі звертаються до URL модуля (`fetch(`${API}/goods…`)`).

Рядок ДОПОВНЮЄ виведене з коду, а не заміняє його (до 2026-10-07 заміняв — і рядок
`/counterparties, /vehicles` ховав 12 сторінок, що беруть контрагента через API: Bug #788).
Потрібен там, де автоматика чогось не бачить — назва модуля ≠ сторінка або UI агрегату
живе на сторінці, яка до URL модуля напряму не звертається:

```
**Модуль:** `apps/api/src/modules/goods/`

**Маршрути UI:** `/catalog`, `/inventory`, `/pricing-rules`
```

Гейт C перевіряє, що кожен названий маршрут існує і має хоч один Playwright-спек.

## Межі

- Цифри кейсів — **лише з `vitest --reporter=json`**. `grep -c "it("` рахує
  коментарі й `it.each` як 1 замість N.
- Фікстура — **factory**, не `const`: `isolate: false` без `clearMocks`.
- У `*.spec-fixture.ts` eslint суворіший: `async` без `await` — error.
- Нічого не «спрощувати» у перенесених кейсах: розбиття змінює структуру, не поведінку.
