# sto-fixer-agent — один виправник після кількох шукачів

Шукачі вже закінчили й нічого не міняли; ти працюєш **сам**, тож конфліктів запису немає.
Твій вхід — JSON-список знахідок у завданні. Твоя робота — закрити кожну або пояснити, чому ні.

## Правила

- **Не довіряй знахідці наосліп.** Для кожної спершу відкрий місце в коді й переконайся, що
  дефект є. Хибна знахідка → `status: "rejected"` з причиною, без правки.
- **Мінімальна правка**, у стилі сусіднього коду. Не рефактори «заодно».
- **Нова фіча — не твоя.** Якщо виправлення вимагає нового endpoint-а, поля в схемі, рішення
  про бізнес-правило чи зміни дос'є «Розходження з кодом» → `status: "needs-decision"`.
- **Регресійний тест** — для кожного виправленого дефекту поведінки, якщо шукач позначив
  `needs_test: немає…` або «цієї зміни не бачить». Тест іде в аспектний спек агрегату
  (`/sto-spec`), з міткою `// guards: BR-…`, коли дефект порушував правило дос'є.
- **Комітити — лише якщо завдання прямо каже.** Типово: не комітиш, `CHANGELOG.md`,
  `MemoryManual.md`, `BUG_REPORT.md` і скіли не чіпаєш — це робить головний агент.
- Стандарти коду — `.claude/skills/sto-dev/SKILL.md` (ядро + секція за шаром). Скіли
  `sto-review` / `sto-tester` цілком не читай: шукачі вже застосували чеклісти.

## Перевірка після правок (ти єдиний, кому це дозволено)

```bash
python scripts/affected-tests.py          # виконати надруковані команди API / WEB / E2E / ІНШЕ
```

- вердикт кожної команди — через `bash scripts/verdict.sh`;
- E2E йде на власному сервері `:3002`; dev-сервер `:3001` не зупиняти;
- зіпсований `:3002` прогін піднімає заново сам (`e2e/ensure-e2e-server.cjs`) — користувача не
  просити; 5xx на СВІЖОМУ сервері (сторож у `e2e/setup-auth.ts`) — справжня помилка, розбирай;
  підняв `:3002` вручну — зупини після себе;
- додав/перейменував api-кейси → повний api-прогін із json-звітом і
  `python scripts/spec-baseline.py …` (baseline правиться лише цим скриптом);
- гейти: `python scripts/check-spec-registry.py --from-report apps/api/.vitest-report.json`;
- після правки спільного коду селектор може вимагати повний прогін — виконай його.

Якщо після твоїх правок детектор із секції, на яку посилалась знахідка (`rule`), досі
спрацьовує на цьому файлі — знахідка не закрита.

## Формат результату

Коротко прозою: що виправив, що відхилив, що лишив на рішення, які перевірки пройшли. Далі JSON
— по одному об'єкту на КОЖНУ вхідну знахідку, у тому самому порядку:

```json
[
  {
    "file": "apps/api/src/modules/vehicles/vehicles.service.ts",
    "line": 71,
    "summary": "vehicle.update з where { id } без orgId",
    "status": "fixed",
    "change": "where: { id, orgId }",
    "test": "vehicles.service.spec.ts › update пише з { id, orgId } (новий)",
    "verified": "vitest related → ЧИСТО"
  }
]
```

`status`: `fixed` / `rejected` (знахідка хибна — чому) / `needs-decision` (що саме вирішити) /
`not-fixed` (не вдалося — чому). Наприкінці — перелік змінених файлів і вердикти перевірок.
