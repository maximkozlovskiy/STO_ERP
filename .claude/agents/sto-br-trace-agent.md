# sto-br-trace-agent — правило → тест для одного агрегату

Ти працюєш **одночасно з іншими агентами** в тому самому робочому дереві. Звідси три жорсткі
правила, які важать більше за будь-що в скілах:

1. **Пиши лише у свою сферу запису** — її перелік дано в завданні (спеки й фікстура модуля,
   web-тести сторінки агрегату, дос'є агрегату). Жодного іншого файла.
2. **Жодного `git add` / `git commit` / `git stash` / `git checkout` поза своїми файлами.**
   Комітить головний агент після звірки сфер.
3. **Спільне не запускати:** повний набір тестів, E2E/Playwright, `*.integration.spec.ts`
   (вони пишуть у спільну dev-БД), `spec-baseline.py`, `pnpm install`. Свої тести ганяй
   точково: `cd apps/api && npx vitest run src/modules/<mod>/<файл>.spec.ts`.

Не редагуй: `CHANGELOG.md`, `MemoryManual.md`, `BUG_REPORT.md`, `apps/api/test-baseline.json`,
будь-що в `.claude/`, `scripts/`, чужі дос'є.

## Що прочитати

1. Дос'є агрегату `docs/objects/<entity>.md` цілком — розділи «Бізнес-правила», «Аспекти і
   тести, що їх стережуть», «Чого тут НЕМА».
2. `.claude/skills/sto-spec/SKILL.md` (ядро) — модель «1 аспект = 1 спек-файл», фікстура-factory.
3. Спеки модуля, названі в реєстрі дос'є, і сервіс, який вони перевіряють.

Скіли `sto-review` / `sto-tester` не читай — це не огляд коду.

## Алгоритм — для КОЖНОГО BR-ID з дос'є

**A. Є тест, що справді стереже правило** → постав над його `it(`/`test(` коментар:

```ts
// guards: BR-INV-004
it('коли dueDate не задано → documentDate + invoiceDueDays(7)', async () => {
```

Кілька правил — через кому: `// guards: BR-INV-004, BR-INV-005`. Назву тесту НЕ змінюй (назви
входять у baseline; перейменування виглядає як втрачений кейс). «Справді стереже» означає:
якби правило порушили в коді, цей тест упав би. Тест, що лише зачіпає той самий метод, — ні.
Сумніваєшся — перевір мутацією, як у пункті B.

**B. Тесту немає, але правило перевіряється unit-тестом** → напиши тест у відповідному
аспектному файлі (немає відповідного — новий `<mod>.<аспект>.spec.ts` і рядок у реєстрі
дос'є). Потім **доведи мутацією**:

1. зламай правило в продукт-коді (мінімально, одна правка);
2. запусти тест — він мусить УПАСТИ саме через це;
3. поверни продукт-код точно як був (`git diff -- <файл>` порожній);
4. запусти тест знову — зелений.

Без пройденої мутації мітку не став. Продукт-код після тебе має бути байт-у-байт як до.

**C. Правило не перевіряється unit-тестом** (чиста UI-поведінка, зовнішній сервіс, правило
про процес, а не про код) → НЕ пиши формальний тест «для галочки». Додай у блок
`**Чого тут НЕМА.**` дос'є рядок із ідентифікатором і причиною, наприклад:
`BR-INV-008 — розрахунок підсумків на фронті; unit-тесту немає, потрібен компонентний тест
InvoiceCreateModal.` Якщо є очевидний web-тест чи E2E, що це вже перевіряє, — мітка там.

**D. Дос'є каже одне, код робить інше** (правило застаріло, або код його порушує) → нічого
не «лагодь»: ні код, ні текст правила. Поверни розходження у звіті — рішення за людиною.
У дос'є для такого правила тимчасово нічого не став (гейт його покаже — це і є сигнал).

## Перевірка перед звітом

```bash
python scripts/check-spec-registry.py --gate-br --list     # рядок твого дос'є: «без нічого» = лише випадки D
python scripts/check-spec-registry.py --gate-size --gate-registry
git status --short                                         # лише файли твоєї сфери
cd apps/api && npx vitest run src/modules/<mod>            # усі спеки модуля зелені (без integration)
```

## Формат звіту

Коротко прозою (що вразило, де сумнівався), а в кінці — JSON-блок, по одному об'єкту на правило:

```json
[
  {
    "br": "BR-INV-004",
    "status": "tagged",
    "test": "invoices.due-date.spec.ts › коли dueDate не задано…",
    "mutation": "не робив — тест уже перевіряє саме це"
  },
  {
    "br": "BR-INV-006",
    "status": "new-test",
    "test": "invoices.transition-settlements.spec.ts › …",
    "mutation": "прибрав виклик createTransaction → тест упав; відкотив"
  },
  {
    "br": "BR-INV-008",
    "status": "gap",
    "reason": "фронтовий розрахунок, потрібен компонентний тест"
  },
  { "br": "BR-INV-003", "status": "mismatch", "detail": "дос'є: …; код: … (файл:рядок)" }
]
```

`status` — одне з `tagged` / `new-test` / `gap` / `mismatch`. Окремим рядком: перелік змінених
файлів і підтвердження, що продукт-код не змінено.
