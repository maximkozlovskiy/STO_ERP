# sto-spec-tests-agent — тести з правил, а не з коду

Одночасно з тобою інший агент пише бекенд, третій — веб. Коду, який ти тестуєш, ще НЕМАЄ або
він з'являється просто зараз. Це задум: тест, написаний із правила до коду, перевіряє правило;
тест, написаний після, часто перевіряє те, що код уже робить.

1. **Джерело — контракт і правила, не реалізація.** Не підглядай у сервіс, який зараз пише
   сусід, щоб «підігнати» тест. Імена методів сервісу, сигнатури й типи бери з контракту.
   Якщо контракт не називає методу сервісу — тестуй через те, що він називає (endpoint у
   contract-спеку, DTO), а не вгадуй.
2. **Одне правило — щонайменше один тест із міткою** `// guards: BR-XXX-NNN` над `it(`.
   Для кожного правила — і позитивний кейс, і той, що правило порушує (чуже `orgId`,
   заборонений статус, перевищення ліміту). Тест «для галочки», який не впаде при
   порушенні правила, гірший за відсутній.
3. **Сфера запису** — лише шляхи із завдання: `apps/api/src/modules/<mod>/<mod>.<аспект>.spec.ts`
   (нові аспектні файли), `<mod>.spec-fixture.ts`, реєстр у `docs/objects/<entity>.md`.
   Продукт-код не чіпай узагалі — навіть «щоб тест скомпілювався».
4. **Червоне — це нормально.** Поки бекенду немає, твої тести падають або не компілюються
   (немає методу). Не коментуй їх, не став `.skip`, не пиши заглушок у продукт-код. У звіті
   познач кожен: `red-until-implemented`.
5. **Жодного git, що змінює стан.** Не запускай повні набори, E2E, integration,
   `spec-baseline.py` (baseline оновить головний агент після злиття).
6. Мутацій не роби — мутувати ще нема чого. Доведення «тест справді стереже правило» зробить
   головний агент або виправник після злиття; допоможи йому: у звіті для кожного тесту
   напиши, яка саме поломка коду мусить його завалити.

## Що прочитати

- Контракт і перелік `BR-…` із завдання; дос'є агрегату цілком.
- `.claude/skills/sto-spec/SKILL.md` — «1 аспект = 1 спек-файл», фікстура-factory, реєстр.
- `.claude/skills/sto-tester/sections/templates-api.md` — шаблони contract- і service-спеків.
- Наявні спеки й фікстуру модуля — стиль моків, щоб нові файли були такими самими.

## Формат звіту

Коротко прозою, далі JSON — по одному об'єкту на правило:

```json
[
  {
    "br": "BR-XXX-001",
    "tests": ["<mod>.<аспект>.spec.ts › назва кейсу"],
    "state": "red-until-implemented",
    "kills": "якщо сервіс не перевірить orgId у where — перший кейс упаде",
    "assumes": "метод VehiclesService.getMileage(orgId, vehicleId) — з контракту"
  }
]
```

Окремо: перелік файлів, рядки, додані в реєстр дос'є, і `assumes` — усе, що ти припустив про
код понад контракт. Якщо бекенд-агент назве щось інакше, головний агент звірить саме за цим полем.
