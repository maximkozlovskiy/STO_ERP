## 1. Борг обробки помилок на фронті — ✅ ЗАКРИТО (2026-10-03)

**264 → 0.** Обидва правила (`no-misused-promises`, `no-floating-promises`) підняті з
`warn` до **`error`** — щоб борг не накопичувався знову: саме через `warn` він і виріс.

Головне уточнення, яке дав розбір: це були **не** «264 мовчазні збої». Більшість
обробників мали try/catch і показували помилку — лінт просто не міг відрізнити легітимний
fire-and-forget від справжньої діри. Тепер намір позначається явним `void` + коментарем
_чому_ (взірець — `lib/cache-invalidation.ts`: TanStack сам тримає error-стан queries).

**Справжні дефекти, знайдені розбором:**

- `CalendarSlotModal` — порожній `catch { /* ignore */ }`: картка клієнта мовчки не
  відкривалась, користувач не розумів, чи клік зареєструвався. → `toast.error` + i18n.
- `WorkOrderMediaSection` — видалення медіа async-обробником **без** try/catch: файл не
  видалявся, користувач не бачив нічого. → механізм `onError`, що вже використовувало
  завантаження в тому самому файлі, + ключ `media.deleteError`.

## 2. Типізація відповідей API — ✅ ЗАКРИТО (2026-10-04)

**Вимір по фактичному документу** (`python scripts/count-untyped-routes.py`):

| Стан                                     | Роутів  |
| ---------------------------------------- | ------- |
| Типізовано                               | **310** |
| Без тіла за призначенням (204 / бінарні) | 109     |
| **БЕЗ ТИПУ**                             | **3**   |

Ті 3 — `/invoices/{id}/pdf`, `/work-orders/{id}/pdf`,
`/counterparties/…/reconciliation-acts/{actId}/pdf`: бінарні відповіді, JSON-схеми не
мають за призначенням. Тобто **борг закрито повністю**.

### Цифра перевизначалась ЧОТИРИ рази — і щоразу через вузький детектор

| Твердження                       | Фактично      | Чому розійшлось                              |
| -------------------------------- | ------------- | -------------------------------------------- |
| «59 контролерів без анотацій»    | 37            | grep не бачив форму `@ApiResponse`           |
| «144 нетипізовані роути»         | 60 потребують | не відділяв 204 і файлові                    |
| «60 справді потребують типу»     | **3**         | рахував як борг ті, де тіла немає за задумом |
| (у списку: settings 7, health 3) | 0 у кожному   | вони вже були типізовані або бодилес         |

Тому вимір тепер **скриптом у репозиторії**, а не регуляркою: `scripts/count-untyped-routes.py`
розділяє три стани (типізовано / без тіла за призначенням / справжній борг) і читає
документ, а не код.

### Що дала типізація — знахідки, не теорія

- колонка «Бренд» у залишках **завжди показувала «—»** — `InventoryService` не включав
  `brand` у `select`, хоча сусідні `byDocument`/`byBatch` віддавали; web маскував кастом;
- `useWorkOrderTransition` писав **довільний рядок** у кеш;
- 4 enum-колонки `BankTransaction` були `string`; `invoiceType` — баг у DTO беку;
- `SavedReport.syncVersion` — `BigInt`, а `main.ts` патчить `BigInt.prototype.toJSON`, тож
  **на транспорті це РЯДОК**. Рукописний інтерфейс описав би його як `number`.

### Межа застосовності, зафіксована на конструкторі звітів

`reports/builder` — ad-hoc: набір колонок задає користувач у рантаймі, `GroupNode`
рекурсивний, `detailRows` — відкрита мапа. Точна схема тут **збрехала б**. Тому
типізовано конверт (`entity`, `columns`, `groupBy`, `rowCount`, `truncated`), а динамічні
частини **явно** позначені вільними обʼєктами. Та сама межа, що й для `ColumnMapping`.

### Пастка: новий DTO може бути ТОЧНІШИМ за сервіс — і помилятись

Проєктуючи DTO «з форми сервісу», я двічі поставив `@ApiPropertyOptional` там, де
реєстр оголошує поле обовʼязковим (`ReportMetadataEntityDto.dateField`,
`ReportMetadataRelationDto.advanced`). `tsc` **не ловить** цей напрямок: сервіс, що
завжди віддає поле, задовольняє й опційний тип. Згенерований тип казав би web-у
«поля може не бути» там, де воно є завжди → зайві `?.` і хибні fallback-и.

Знайшли це **рукописні типи фронта** при міграції на згенеровані — вони були
правильні, а DTO ні. Висновок: якщо для тієї самої форми вже існує рукописний тип
(на фронті чи в сервісі), його треба звірити з новим DTO в ОБИДВА боки, а не лише
покластись на компілятор.

### Чому анотація не декоративна

Усі 14 методів звітів мають **явний тип повернення**, тож `tsc` звіряє DTO з сервісом.
Перевірено пробною поломкою (`totalRevenue` `number` → `string`): помилка назвала поле і
фактичний тип — `Type 'Money' is not assignable to type 'string'`.

## 3. Гроші у `number` — ✅ ЗАКРИТО по API (2026-10-03)

**`roundMoney` у прод-коді API = 0.** `Money` застосовано до:

- `common/utils/vat.ts` — спільний суматор для invoices, reports, work-orders;
- **`payroll.calculator.computeAccrued`** — серце нарахування зарплати; усі точки, що
  беруть результат, успадковують тип;
- **`settlements-account`** — `periodDelta` і `openingBalance` акта звірки;
- **`invoices.service`** — 10 `roundMoney` → `money`, плюс 7 читань із БД через
  `moneyFromDecimal` (див. нижче про межу застосування);
- **`work-orders.service` + `work-order-stock-effects`** — блок WO-H2 (totalLabor /
  totalActualLabor / totalParts / totalAmount) і база для `SUPPLIER_CHARGE`;
- **`purchase-orders.service`** — тотали create/update, `receivedAmount`;
- **`cash.service`** — баланси каси; `getBalance`/`getBalances`/`computeBalance`
  тепер **повертають `Money`**, тож тип успадковують усі виклики;
- **`payments.service`** — FX-різниця;
- **`payroll.service`** — база нарахування з `::float`-SQL, тотали;
- **`completion-acts`** — юридичний PDF-акт;
- **`supplier-returns`**, **`supplier-payments`** — тотали, `newPaid`, FX;
- **`loyalty`** — лише `discountAmount` (бали × курс = ₴); самі бали — `roundPoints`;
- **`reports.service`** — місце Bug #629 (дрейф × 0.4 у CSV-експорті); `margin` лишився
  відсотком;
- **`xlsx`** — тотали імпорту документа.

Для settlements це **профілактика, не фікс бага**: заміряно 66 352 випадки дрейфу зі
100 000, але величина ≈2e-11 — нижче за розрядність `Decimal(12,2)`, і `openingBalance`
читається з БД уже округленим Postgres. Користь типу в тому, що він не дасть **потім**
забути округлення.

### Межа застосування, встановлена на invoices

Не кожен `Number(row.amount)` варто брендувати. У `invoices.service` їх було ~37, але
перетворено **7** — ті, де значення **годує арифметику**, результат якої пишеться назад:
`invoiceAmount` → FX-конверсія, `paymentRemaining` → сума `SettlementTransaction`,
`clonedAmount` → amount нового рахунку, `existing.unitPrice` → множник у `priceWithoutVat`,
і три `*Base`-агрегати → різниця `FX_LOSS`/`FX_GAIN`.

Решта ~30 — мапінг `Decimal`→JSON у `toResponseDto`. Там значення вже округлене Postgres,
нової арифметики немає, і бренд нічого не стереже — лише **розмиває сигнал**: якщо
`moneyFromDecimal` стоїть скрізь, він перестає означати «тут рахують гроші».
`vatRate` теж лишається `Number()` — це ставка, не сума.

**Правило для наступних модулів:** брендувати точки обчислення, не точки серіалізації.

### Баг, який знайшла сама міграція

`moneyFromDecimal` приймала лише `{toNumber}|number`. Виглядало правильно — Prisma
`Decimal` має `toNumber`. Але функція стоїть РІВНО там, де був `Number(x)`, а `Number()`
конвертує через `toString`/`valueOf`: кожен із 44 викликів був латентним `TypeError` на
raw-SQL рядках, `::text`-кастах і Decimal-подібних обгортках.

Впало на 2 payroll-специв (у наборі 14 фікстур мокають Decimal як `{toString}`).
**Без цього покриття воно впало б у проді.** Контракт розширено, +4 тести. Урок
записано в `docs/GOTCHAS.md`.

**Лишається** (не Money-борг, а загальний): 97 грошових конверсій `Number()`/`toNumber()`
у 26 файлах — це переважно мапінг `Decimal`→JSON у `toResponseDto`, який за MP-B13
брендувати НЕ треба. Вимір за вузьким патерном (
`Number(x.*amount|price|total|sum|cost|balance|paid|vat|debt)` плюс `.toNumber()`, без
spec-файлів). Цифра **не порівнювана** з «222 у 55» з аудиту: там патерн був ширший і
включав негрошові конверсії. Наступні кандидати — модулі, де гроші **обчислюються**:
`work-orders`, `purchase-orders`, `reports`.

**Пріоритет: середній.**

**ЦИФРА В БОРЗІ БУЛА ЗАНИЖЕНА — вчетверте в цьому аудиті.** Документовано «29 у 14
файлах», фактично 42 у 13: grep шукав `toast.x('рядок')` і не бачив шаблонів з

цифру замість виміряти її. Детектор, що покриває обидві форми:

```bash
grep -rnE "toast\.(error|success|info|warning)\(\s*(['\"\`])[^'\"\`]*[Ѐ-ӿ]"   apps/web/src --include=*.tsx --include=*.ts
```

Інтерполяція пішла в i18next-плейсхолдери (`{{number}}`, `{{count}}`), а не в
склеювання рядків — інакше порядок слів не перекладається.

**Супутня регресія, виправлена одразу:** 8 × `react-hooks/exhaustive-deps` — `t`
вживалось у `useCallback` без потрапляння в deps. Не косметика: захоплене `t`
показало б попередню мову після перемикання (та сама пастка, що нижче).

## 4a. Пастка, знайдена при міграції toast-ів на i18n

`useTranslation()` у callback-у з `deps: []` дає **захоплене** `t`. Для більшості
повідомлень це нешкідливо, але в `useLanguage` toast спрацьовує **після** перемикання
мови — і показав би попередження саме тією мовою, яку користувач щойно покинув.

```ts
// ❌ у callback із deps [], що виконується після зміни мови
const { t } = useTranslation('common');
… .catch(() => toast.warning(t('language.savedLocallyOnly'))); // попередня мова

// ✅ i18n.t читає активну мову в момент виклику
import i18n from '@/i18n/config';
… .catch(() => toast.warning(i18n.t('common:language.savedLocallyOnly')));
```

Правило: `useTranslation` — для рендеру; `i18n.t` — для відкладених колбеків, які
можуть пережити зміну мови.

**Супутнє, не toast:** `useWorkOrderActions:183` звіряє `msg.includes('вже існує')` —
український **підрядок помилки бекенда**. i18n на фронті цього не лікує; потрібен код
помилки замість тексту на боці API.

## 5a. Чому ці 185 тестів — не «покриття для покриття»

Перед написанням усі 12 модулів **проаудитовано** на порушення інваріантів: 4 мали hard
`.delete()`, але всі чотири законні — `Comment`, `serviceWork`/`serviceGood` **не мають
колонки `deletedAt`** (hard-delete за задумом схеми). Жодного порушення CLAUDE.md §5.
Тож ці тести — **guard-и**, а не фікси багів; у комітах це сказано прямо.

**Кожен доведений мутацією**: у прод-код вносилась поломка, перевірялось, що падає РІВНО
цільовий тест, потім відкат. Разом 19 поломок на три партії. Один тест спершу **не впав**
(ловив `deletedAt` у JOIN замість основної таблиці) — його посилили, а не лишили як є.

Найцінніші guard-и, перевірені особисто:

- **bull-board.guard** — зламано так, щоб роль бралась із JWT-payload, а не з БД: тест
  упав. Без нього рефакторинг, що починає довіряти `role` з токена, дав би механіку доступ
  до адмінки черг BullMQ (ескалація привілеїв);
- **work-order-media** — MinIO переставлено перед БД: 3 падіння. Саме той наслідок, про
  який попереджає коментар у коді — збій MinIO лишив би рядок БД на видалений файл, тобто
  вічно биті signed-URL;
- **services** — `deleteMany` переставлено перед валідацією: падіння. Невалідний ввід зніс
  би наявний склад пакета (реальна втрата даних);
- **maintenance-schedules** — `addDaysKyiv` замінено на `setDate`: падіння на переході DST
  (CAL-M3 — зсув дати наступного ТО на ±1 день).

Побічно `sto-tester` отримав **false-positive guard**: перед тим як позначити hard-delete
багом, звірити схему на наявність `deletedAt` — інакше тестер «виправив» би робочий код у
нерабочий.

## 5b. Повний E2E у CI — і що він одразу знайшов (2026-10-04)

До цього CI ганяв **14 тестів із 354**. Додано job `e2e-full` (push у `main` +
`workflow_dispatch`); `e2e-smoke` лишається на кожен PR для швидкого відгуку.

**Перший же повний прогін знайшов Bug #779** — CORS віддавав
`access-control-allow-methods: GET,HEAD,POST`, тож браузер блокував **кожен** cross-origin
`DELETE`/`PATCH`/`PUT`. Причина: на Fastify `enableCors` делегує у `@fastify/cors`, чий
дефолт вужчий за Express-івський. Не ловилось нічим іншим: API-тести ходять повз CORS
(`curl -X DELETE` доходив до guard-а), у проді web — той самий origin за Caddy, а smoke не
створює фікстур.

| Прогін       | passed | failed                      | flaky |
| ------------ | ------ | --------------------------- | ----- |
| 1 (до фіксу) | 276    | **15** (+63 не запустились) | —     |
| 2 (після)    | 349    | 0                           | 5     |
| 3 (теплий)   | 352    | 0                           | 2     |

Flaky **не повторюються** між прогонами — різні тести щоразу, жоден не закріпився. Це
таймінг, який закриває наявний `retries: 2`, а не зламана поведінка. Тримати їх під
наглядом варто: якщо котрийсь почне падати стабільно — це вже регресія.

**Побіжно — реальний ризик:** жоден job не мав `timeout-minutes`, тобто при зависанні
сервера висів би до GitHub-дефолту **6 годин**. Поставлено 20 (smoke) і 40 (full, запас ×8
до виміряних ~5 хв).

## 6a. Бюджет бандла і a11y — що саме зроблено, а що свідомо ні (2026-10-04)

**Бюджет.** Спершу виміряно, потім поставлено ліміт — не навпаки: бандл **1.28 MB gzip**,
first load сторінок 408–512 KB gzip (найважча `/invoices`). Дві перевірки, бо міряють різне:

| Команда                             | Що міряє                       | Ліміт       |
| ----------------------------------- | ------------------------------ | ----------- |
| `pnpm --filter @sto/web size`       | сумарний JS бандла             | 1.4 MB gzip |
| `pnpm --filter @sto/web size:pages` | first load КОНКРЕТНОЇ сторінки | 560 KB gzip |

Другу довелось писати скриптом: `size-limit` для glob рахує **суму** всіх файлів
(перевірено — `chunks/*.js` дає ті самі 1.28 MB), тож запис із назвою «найбільший чанк»
вимірював би зовсім не те, що обіцяє назва. Скрипт читає, які чанки **реально згадані в
HTML** сторінки. До імен чанків не прив'язуємось — Turbopack дає хеші без стабільних
`framework`/`main`.

**A11y — режим храповика, і це свідомо.** У застосунку вже **39 порушень**
serious/critical шести типів:

| Правило                       | Вузлів | Суть                                    |
| ----------------------------- | ------ | --------------------------------------- |
| `color-contrast`              | 15     | тема не дотягує 4.5:1 на частині тексту |
| `select-name`                 | 9      | рідні `<select>` без `aria-label`       |
| `button-name`                 | 6      | кнопки-іконки без доступного імені      |
| `scrollable-region-focusable` | 3      | прокрутка без доступу з клавіатури      |
| `label`                       | 3      | поля форми без звʼязаного label         |

Тест, що падає з першого дня, вимикають — користі нуль. Тому поіменна базова лінія по
сторінках: набір валиться лише на **новому** правилі або розповзанні наявного на нову
сторінку. Є і зворотний бік — окремий тест вимагає **прибирати з лінії вже виправлене**,
інакше список розростається і перестає відображати реальність.

**Чого НЕ зроблено:** самі 39 порушень не виправлено. Це багатофайлова робота (голі
`<select>` у calendar/counterparties/reports, контраст теми) — окрема задача, а не
прибирання боргу інструментів; наосліп ризикує зламати верстку. **Борг зафіксовано і він
не росте** — це і було метою пункту.

**`autoArchiveDays`.** Поле редагується в UI, але споживача немає. Реалізація =
черга + процесор + scheduler + FSM-перехід, тобто фіча. Натомість зроблено головне:
підказка під полем чесно каже, що налаштування поки не діє, а значення збережеться —
раніше користувач налаштовував те, що тихо нічого не робить.

## 7. Розходження «дос'є ≠ код» — 17 відкритих (2026-10-07)

Знайдено під час розмітки «правило → тест»: агент на кожен агрегат зіставляв кожне `BR-…` із
кодом. Де дос'є каже одне, а код робить інше — він нічого не лагодив. Вісімнадцяте (BR-WO-001,
акт писав статус наряду повз FSM) було справжнім багом у грошовому ланцюгу й виправлене
одразу. Решта 17 — тут, за рішенням власника.

Кожне розходження записане в блоці «**Розходження з кодом.**» свого дос'є; гейт D
(`check-spec-registry.py`) його не блокує, але показує окремою колонкою. Закриття пункту =
прибрати запис із блока І або поставити мітку `// guards:` на тест, або виправити текст правила.
