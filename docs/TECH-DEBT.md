## 1. Борг обробки помилок на фронті — ✅ ЗАКРИТО (2026-10-03)

**264 → 0.** Обидва правила (`no-misused-promises`, `no-floating-promises`) підняті з
`warn` до **`error`** — щоб борг не накопичувався знову: саме через `warn` він і виріс.

Головне уточнення, яке дав розбір: це були **не** «264 мовчазні збої». Більшість
обробників мали try/catch і показували помилку — лінт просто не міг відрізнити легітимний
fire-and-forget від справжньої діри. Тепер намір позначається явним `void` + коментарем
_чому_ (взірець — `lib/cache-invalidation.ts`: TanStack сам тримає error-стан queries).

**Справжні дефекти, знайдені розбором:**

- `CalendarSlotModal` — порожній `catch { /* ignore */ }`: картка клієнта мовчки не
  відкривалась, користувач не розумів, чи клік зареєструвався. → `toast.error` + i18n.
- `WorkOrderMediaSection` — видалення медіа async-обробником **без** try/catch: файл не
  видалявся, користувач не бачив нічого. → механізм `onError`, що вже використовувало
  завантаження в тому самому файлі, + ключ `media.deleteError`.

## 2. Анотація контролерів — механіка

**144 роути з 422** не віддають тип відповіді. Виміряно по самому `openapi.json`, а не
грепом по контролерах — попередня цифра «59 із 67 контролерів» була **завищена**: мій
grep шукав лише `@ApiOkResponse`, а частина модулів (напр. `payroll`) анотована через
`@ApiResponse({ status: 200, type })`. Реально неанотованих контролерів 37, і 278 роутів
уже мають тип.

Розподіл нетипізованих за модулями: `reports` 13, `counterparties` 9, `settings` 8,
`work-orders` 7, `goods` 6, `stock-items` 6, `pricing-rules` 5, `xlsx` 5, `auth` 4.

Уже анотовано 8 (invoices + 7 модулів із залишку аудиту) — і це дало **реальні знахідки**:
`useWorkOrderTransition` писав довільний рядок у кеш, 4 enum-колонки `BankTransaction`
були `string`, `PreviewCandidateDto` взагалі не потрапляв у Swagger.

**Ціна:** ~10–15 хв на контролер, разом ~1.5 дня. Підводний камінь — методи з inline-формами
(`Promise<{ id, number }>`): для них спершу потрібен DTO.

**Пріоритет: середній.** Цінність спадає — у довідниках і налаштуваннях менше FSM-станів,
тож менше шансів на такі самі діри. Варто брати модулі з перехідними станами.

## 3. Гроші у `number` — розширено (2026-10-03)

`Money` застосовано до:

- `common/utils/vat.ts` — спільний суматор для invoices, reports, work-orders;
- **`payroll.calculator.computeAccrued`** — серце нарахування зарплати; усі точки, що
  беруть результат, успадковують тип;
- **`settlements-account`** — `periodDelta` і `openingBalance` акта звірки.

Для settlements це **профілактика, не фікс бага**: заміряно 66 352 випадки дрейфу зі
100 000, але величина ≈2e-11 — нижче за розрядність `Decimal(12,2)`, і `openingBalance`
читається з БД уже округленим Postgres. Користь типу в тому, що він не дасть **потім**
забути округлення.

**Лишається:** 222 конверсії `Number()`/`toNumber()` у 55 файлах поза типом. Бренд робить
правильний шлях найлегшим, **а не єдиним**. Наступні кандидати — `invoices` (41
конверсія в одному сервісі), далі модулі, де гроші обчислюються, а не просто проходять.

**Пріоритет: середній.**

## 4. Свідомо відкладене — із виміряною ціною

### TypeScript 7

Чекає на `typescript-eslint` 7.1. Інструмент каже прямо: `does not support TS 7.0`.
Залишити TS 7 означало б зламати лінт у всьому проєкті.

### `api → ESM`

**Виміряно** (не оцінено):

| Конфігурація                        | Помилок        |
| ----------------------------------- | -------------- |
| `module: node16` + `type: module`   | 1917           |
| + `rewriteRelativeImportExtensions` | 499            |
| залишок                             | 493 × `TS1479` |

Корінь: NestJS 12 — `"type": "module"`, а Prisma, BullMQ, ioredis, ExcelJS — CommonJS.
Перехід не усуває розрив, а **перевертає** його. Плюс 279 файлів із декораторами на
`emitDecoratorMetadata`, який в ESM поводиться інакше.

Єдина мета міграції — розблокувати TS 7, який сам чекає на тулчейн. **Робити зараз
передчасно.**

### Prisma 8

У release candidate. Не чіпати. Пересторога: `prisma@latest` у реєстрі вказує саме на rc —
наївний `pnpm up --latest` затягнув би його у прод.

## Що НЕ є боргом, хоч виглядає так

**2730 eslint-попереджень в `apps/api`.** З них **2529 — у spec-файлах**: `any`-мокі, що
навмисно описують лише потрібні методи. Це нормальна практика тестів, і підняття їх до
`error` зробило б вивід нечитомим. Реальний борг — ~200 попереджень у прод-коді, на межі
з Prisma.

**Покриття 62%, а не 78%.** Vitest 2 рахував лише файли, які **імпортувались** тестами;
Vitest 5 бере весь `include`. 78% приховувало непокриті модулі — 62% чесніше.
