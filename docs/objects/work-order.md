## Prisma модель

```prisma
model WorkOrder {
  id               String           @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  orgId            String           @db.Uuid
  number           String           // авто-генерується DocumentNumberService.next()
  status           WorkOrderStatus  @default(DRAFT)
  priority         WorkOrderPriority @default(NORMAL)
  vehicleId        String?          @db.Uuid
  counterpartyId   String?          @db.Uuid
  branchId         String           @db.Uuid
  liftId           String?          @db.Uuid
  plannedHours     Decimal?         @db.Decimal(8,2)
  actualHours      Decimal?         @db.Decimal(8,2)
  description      String?
  completedAt      DateTime?
  createdAt        DateTime         @default(now())
  updatedAt        DateTime         @updatedAt
  deletedAt        DateTime?
  syncVersion      BigInt           @default(0)

  lines            WorkOrderLine[]
  parts            WorkOrderPart[]
  calendarSlots    CalendarSlot[]
  invoices         Invoice[]
}
```

**Відносини:**

- → `Vehicle` (M:1 через `vehicleId`, optional)
- → `Counterparty` (M:1 через `counterpartyId`, optional)
- → `GarageBranch` (M:1 через `branchId`)
- → `Lift` (M:1 через `liftId`, optional)
- ← `WorkOrderLine[]` (роботи)
- ← `WorkOrderPart[]` (запчастини)
- ← `CalendarSlot[]` (слоти календаря)
- ← `Invoice[]` (рахунки)
- → `Currency` (M:1 через `currencyId`, optional — мультивалюта Фаза 3)

> **Мультивалюта (Фаза 3, 2026-09-14):** WorkOrder += `currencyId`/`totalAmountBase`/`rateUsed`.
> `totalAmount`/`totalLabor`/…/`paidAmount` — у **валюті наряду**; `totalAmountBase` — тотал у базовій
> валюті org по курсу на `documentDate` (recalcTotals; fallbackToLatest). CHARGE (COMPLETED) і
> CREDIT_NOTE (COMPLETED→CANCELLED) пробрасують `currencyId`+`date` у settlement → борг у base. Оплата
> наряду має бути у валюті наряду (WO.paidAmount += сума у валюті). FX-різниці — поза Фазою 3.

## FSM

```
DRAFT       → ESTIMATE, CANCELLED
ESTIMATE    → APPROVED, DRAFT, CANCELLED
APPROVED    → IN_PROGRESS, ON_HOLD, CANCELLED
IN_PROGRESS → ON_HOLD, COMPLETED            (скасувати можна лише через ON_HOLD)
ON_HOLD     → IN_PROGRESS, CANCELLED
COMPLETED   → INVOICED, CANCELLED           (скасування повертає запчастини й сторнує борг)
INVOICED    → PAID
PAID        → ARCHIVED
```

Джерело правди — `WORK_ORDER_TRANSITIONS` у `work-orders.fsm.ts`; прямого переходу
`IN_PROGRESS → CANCELLED` немає.

> COMPLETED→CANCELLED (C2) реверсує склад+борг (див. side-effects). INVOICED/PAID/ARCHIVED
> **незворотні** (там уже рахунок/гроші) — CANCELLED з них заборонено FSM.
>
> **Єдиний зворотний шлях — сторно оплати з каси (BR-CASH-024): `PAID → INVOICED`.** Це НЕ перехід
> `WORK_ORDER_TRANSITIONS` (зворотного ребра в карті немає й не буде — кнопкою «розоплатити» наряд
> не можна): статус пише внутрішній `reopenPaidWorkOrderInTx` (`work-order-status.ts`, один із двох
> файлів, що пишуть статус наряду) — CAS по статусу `PAID` і прочитаному «сплачено», разом зі
> зменшенням `paidAmount` на суму сторнованої оплати. Side-effects (резерв, списання, нарахування)
> у цьому русі немає. Єдиний викликач — `PaymentsService.reverse`. Сторно оплати наряду в `ARCHIVED` — 400.

Файл FSM: `apps/api/src/modules/work-orders/work-orders.fsm.ts`

> **A3:** stock+settlement side-effects переходів винесено з `WorkOrdersService.transition` у
> `WorkOrderStockEffectsService` (`work-order-stock-effects.service.ts`): `reserveParts` /
> `releasePartReservations` / `writeOffPartsAndCharge` / `returnPartsAndCredit`. `transition()` делегує їх,
> передаючи той самий `tx` — ефекти лишаються атомарними зі зміною статусу.

| Перехід                        | Side-effects (у `$transaction`)                                                                                                                                                                                                                                                                                                                   |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| → `IN_PROGRESS`                | Дорезервувати лише бракуюче: `потрібно − net-резерв наряду`, не більше `available`; нестача не блокує перехід (BR-WO-021)                                                                                                                                                                                                                         |
| → `COMPLETED`                  | RESERVATION_RELEASE → WRITEOFF → `SettlementsService.createTransaction(CHARGE)` (у цьому порядку)                                                                                                                                                                                                                                                 |
| → `CANCELLED` (не з COMPLETED) | Зняти весь net-резерв наряду за картою рухів (з будь-якого статусу, BR-WO-021); OPEN-позиції списків купівлі → CANCELLED (BR-PL-013)                                                                                                                                                                                                              |
| → `CANCELLED` з COMPLETED (C2) | `returnPartsAndCredit`: per part `createMovement(RETURN, +baseQty)` (StockItem++ + `returnToBatch` у ті самі партії) → один `SettlementsService.createTransaction(CREDIT_NOTE)` = сума CHARGE. Реверс `writeOffPartsAndCharge`. Резерв НЕ відновлюється (на COMPLETED уже знято). Single-shot через in-tx status re-read + термінальний CANCELLED |

**Друк (BR-WO-013).** До «Виконано» картка друкує кошторис («Друк», «Зберегти як» через токен
поширення), як раніше. Від «Виконано» — «Друк наряду» (серверний PDF, вікно друку відкривається
до запиту) і «Зберегти PDF»; «Друк рахунку» — коли рахунок наряду є і роль може його друкувати
(OWNER, ADMIN, ACCOUNTANT, RECEPTIONIST — `INVOICE_PRINT_ROLES` у `hooks/useWorkOrderActions.ts`).
Картка — `useWorkOrderActions` (`canPrintOrder`, `canPrintInvoice`); сторінка — «Друк наряду» і
«Зберегти PDF» (`WorkOrderPrintButtons`), «Друк рахунку» в секції рахунку (`InvoiceSection`).
Для наряду, позначеного на видалення, серверного друку немає (BR-WO-012).

**Оплата (BR-PAY-020, BR-WO-016).** «Оплатити» — у картці й на сторінці наряду для статусів
`WO_PAYABLE_STATUSES` і ролей `PAYMENT_CREATE_ROLES`; вікно `ClientPaymentModal` («Аванс за нарядом» до
«Виконано», «Оплата наряду» після). Ручного переходу «Оплачено» в меню статусу немає. Після оплати,
переходу й підписання акта статус і «Сплачено» беруться з сервера (наряд міг сам стати «Оплачено»).
Підсумки показують «Залишок до сплати» (`WorkOrderTotals.tsx`).

**Планові дати (BR-WO-019, BR-WO-020).** Планові «Дата та час початку / завершення» картки — пікер
з мінімальним моментом «зараз» (минулі дні недоступні, сьогодні — години від поточної) і робочими
годинами філії наряду (`GET /settings/work-hours?branchId=`; початок — до години закриття,
завершення — включно з «HH:00» закриття); вибір дня ставить першу доступну годину; поле можна
очистити. Автокінець за нормогодинами й нормогодини між датами рахують лише робочий час філії
(ніч не рахується). Запис календаря наряду переносить сервер при збереженні — діалогу «Оновити
слот?» і `PATCH /calendar/slots/by-work-order` (ендпоінт видалено, BR-WO-026) картка більше не має; після збереження відкритий
календар перечитує записи (`lib/calendar-events.ts`). Планове завершення (`dueDate`) у «Реквізитах»
сторінки наряду й у колонці списку — лише перегляд: дата без часу ставила б північ (поза робочими
годинами) і зсувала запис календаря; змінюється в картці разом із часом і початком.

**Журнал змін (рішення власника 2026-10-16).** Блок «Журнал змін» на сторінці наряду бачать лише

## Бізнес-правила (BR-WO)

- **BR-WO-001**: FSM: тільки через `WORK_ORDER_TRANSITIONS` map — ніколи прямий `update({ status })`
- **BR-WO-002**: RESERVATION → RELEASE → WRITEOFF порядок обов'язковий (guard `available >= qty`)
- **BR-WO-003**: WO parts loops — **sequential** for-loop (shared StockItem composite key — unsafe to parallelize)
- **BR-WO-004**: Номер авто-генерується: `DocumentNumberService.next(orgId, 'WorkOrder')`
- **BR-WO-005**: `plannedHours` / `actualHours` — `Float?`: порожнє означає «не задано», а `0` —
  це значення (нуль фактичних годин не підміняється нормо-годинами)
- **BR-WO-006**: Скасування наряду скасовує чернетки його актів виконаних робіт (у тій самій
  транзакції; підписані акти не чіпаються). Акт скасованого наряду не підписується → 400.
  Наряд у `INVOICED` / `PAID` / `ARCHIVED` акт підписати дозволяє (Bug #795)
- **BR-WO-007**: Сума наряду до сплати містить ПДВ у всіх режимах. `totalAmount` — сума до сплати
  (її бере борг клієнта при `COMPLETED` і рахунок), `totalNet` — сума без ПДВ; інваріант
  `totalNet + totalVat = totalAmount`. За режимом організації: без ПДВ — обидві дорівнюють сумі
  рядків; «ПДВ у ціні» — `totalAmount` = сума рядків, `totalNet` = сума рядків − ПДВ; «ПДВ зверху»
  — `totalNet` = сума рядків, `totalAmount` = сума рядків + ПДВ. Тотали пише лише
  `WorkOrderTotalsService.recalc` — у тій самій транзакції, що змінила рядки: правка роботи чи
  запчастини, клонування наряду, авто-рядки з огляду авто. XLSX-імпорт запчастин допускає
  частковий успіх (рядки пишуться поодинці, поза спільною транзакцією), тому перераховує тотали
  один раз одразу після запису, окремою транзакцією, і лише якщо щось записано. «Сума рядків» —
  це сума ОКРУГЛЕНИХ до копійки рядків (робота: фактичні години × ціна; запчастина: її `amount`),
  тож рядки будь-якого документа складаються в підсумок наряду; ПДВ рахується один раз від суми.
  Наряди, завершені до 2026-10-08, не перераховані: у них `totalNet = totalAmount`, `totalVat = 0`
  (ПДВ зверху клієнтові не нараховували)
- **BR-WO-008**: Перехід у `COMPLETED` перераховує тотали наряду за чинними режимом і ставкою ПДВ
  у тій самій транзакції, ДО нарахування боргу: наряд, створений до зміни налаштувань ПДВ і
  завершений без правки рядків, боргує клієнта за новим режимом. До завершення відкритий наряд
  може показувати суму, пораховану при останній правці рядків
- **BR-WO-009**: **Зведення по табличних частинах документа** (рішення власника 2026-10-13; спільне для наряду, рахунку, закупівлі, складського документа й повернення постачальнику — показується в боковій панелі списку). Для кожної непорожньої таблиці: рядків; найменувань — скільки РІЗНИХ товарів / робіт (два рядки одного товару — одне найменування); сума по рядках — кількість, а для робіт наряду нормо-години (у рядка роботи наряду кількості немає). У рахунку рядок із роботою — «роботи», із товаром — «товари», без обох — «інше» (у «іншого» найменувань стільки ж, скільки рядків). Видалені рядки не рахуються; сума кількості — проста сума чисел, одиниці виміру не зводяться. Рахує сервер агрегатами бази (не клієнт із довантаженого документа, який обрізає рядки). Доступ — ролі списку відповідного документа; документ чужої організації → 404; документ, позначений на видалення, зведення має. Модуль `lines-summary` (`LinesSummaryService`), endpoint `GET /<документ>/:id/lines-summary`
- **BR-WO-010**: **Виконавці наряду у зведенні** — беруться з рядків робіт (`employeeId`): на кожного виконавця число його рядків робіт і сума нормо-годин. Порядок: більше нормо-годин — вище, далі більше робіт, далі за іменем. Звільнений (видалений) працівник лишається у переліку зі своїм іменем. В інших документах рядки виконавця не мають — перелік порожній. Модуль `lines-summary` (`LinesSummaryService.forWorkOrder`)
- **BR-WO-011**: **Правка рядка роботи зберігає роботу й виконавця.** `PATCH /work-orders/:id/lines/:lineId` пише в рядок нові `workId` і `employeeId` (з виконавця рядка рахуються зарплата і блок «Виконавці», BR-WO-010). Нова робота й новий виконавець мають існувати в організації і не бути видаленими — інакше 404, рядок не змінюється. Перевіряється лише ЗМІНЕНЕ значення: картка наряду шле роботу й виконавця кожного рядка при кожному збереженні, тому рядок із уже видаленою роботою чи звільненим виконавцем зберігається далі. Години й ціна при зміні роботи беруться із запиту (або лишаються як були), з довідника робіт не підтягуються. У статусах «В роботі» / «Призупинено» правляться лише фактичні години — зміна роботи чи виконавця там дає 400 (Bug #836)

Це стосується «свого» механіка запису (форма шле збереженого механіка щоразу). Механік, обраний у формі явно разом із перев'язкою, і механік нового запису («+ Слот», створення з планшета) — вибір користувача: не закріплений за підйомником → 400 (у синхронізації — конфлікт), як у формі при зміні часу чи підйомника (BR-WO-024). Так само 400, коли новий наряд без дат бере підйомник, змінений у формі, а свій механік за ним не закріплений. Коли механіка перевірено за підйомником НАРЯДУ, а не форми, відповідь називає підйомник наряду («не закріплений за підйомником наряду «…»»; наряд без підйомника — окремий текст, Bug #909).
- **BR-WO-029**: **Склад рядка товару — вільна кількість і автовибір** (рішення власника 2026-10-21). У картці наряду й у вікні «+ Запчастина» список «Склад» рядка товару, коли товар обрано, показує біля кожного складу ВІЛЬНУ кількість цього товару (`available = quantity − reserved`, BR-INVT). Щойно товар обрано (пошуком чи вікном вибору), склад підставляється сам: вільна кількість є лише на одному складі → цей склад; на кількох → основний (`isMain`), якщо на ньому вільна є; на кількох, але не на основному → поле порожнє, обирає людина; вільної немає ніде → основний склад; залишки отримати не вдалося — так само (основний), підписи без кількості. Вільна кількість округлюється до 3 знаків, як показ (`fmtQty`): float-дрейф суми рухів вільним не рахується. Рахуються лише склади зі списку вибору (без видалених і «Шинного готелю»). Ручний вибір складу не перезаписується, доки не змінено товар. Нестача вільного залишку не блокує додавання (BR-WO-021); індикатор лише попереджає (рішення власника 2026-10-22). Збереженого рядка правило не стосується (склад незмінний, BR-WO-021); колонка «На складі» лишається фізичною кількістю.
