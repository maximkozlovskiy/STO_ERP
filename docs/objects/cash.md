# Cash / Каса — Dossier

> Рух готівки в касах: внесення (cash-in) та видача (cash-out), баланс каси, статті витрат.
> ЄДИНА точка руху готівки — `CashService.createOperation` (аналог `SettlementsService.createTransaction`).

---

## Prisma моделі

```prisma
enum CashDirection { IN OUT }
enum CashOperationReason {
  // внесення
  SALE_PAYMENT        // оплата контрагента (клієнт; створює Payment)
  SUPPLIER_REFUND_IN  // повернення від постачальника
  ADVANCE_RETURN      // повернення підзвітних коштів (працівник)
  BANK_WITHDRAWAL     // отримання готівки з банку
  OWNER_IN            // внесок власника
  COLLECTION          // інкасація / виїмка
  MANUAL_IN           // довільне внесення
  // видача
  REFUND              // повернення клієнту
  SUPPLIER_PAYMENT    // оплата постачальнику (створює і проводить SupplierPayment)
  ADVANCE_ISSUE       // видача під звіт (працівник)
  BANK_DEPOSIT        // здача в банк
  OWNER_OUT           // вилучення власником
  EXPENSE             // витрата (стаття обов'язкова)
  PAYROLL             // виплата ЗП (лише авто з відомості, вручну заборонено)
  MANUAL_OUT          // довільна видача
}

model CashRegister {           // + до наявних полів:
  isFiscal       Boolean @default(false)  // фіскальна → операції лише у відкриту зміну + ПРРО
  initialBalance Decimal @default(0) @db.Decimal(12,2)
  operations     CashOperation[]
}

// Append-only (шаблон SettlementTransaction: без deletedAt/updatedAt/syncVersion).
model CashOperation {
  id, orgId, cashRegisterId, cashShiftId?  // cashShiftId — для фіскальної каси
  direction CashDirection, amount Decimal(12,2)   // amount>0, знак з direction (валюта каси)
  amountBase?, rateUsed?                          // у базовій валюті по курсу на дату
  reason CashOperationReason
  expenseCategoryId?  // стаття руху коштів
  counterpartyId?, employeeId?   // контрагент | працівник (залежно від приводу)
  documentType?, documentId?     // ПЛАТІЖНИЙ документ рядка: 'Payment' | 'SupplierPayment' | 'PayrollPeriod'
  baseDocumentType?, baseDocumentId?  // ПІДСТАВА: 'WorkOrder' | 'PurchaseOrder' (BR-CASH-020)
  notes?, createdBy?, createdAt
  // @@index([orgId,cashRegisterId,createdAt]) [orgId,cashShiftId] [orgId,reason,createdAt]
}

model ExpenseCategory {        // дерево статей руху коштів (per-org)
  id, orgId, parentId?, name, sortOrder, isActive, syncVersion, createdAt, updatedAt, deletedAt?
  type ExpenseCategoryType     // EXPENSE (видача) | INCOME (внесення); гілка дерева одного типу
  defaultReason CashOperationReason?  // привід за замовчуванням (BR-CASH-022)
  // @@unique([orgId,name]); частковий unique-індекс "expense_categories_default_reason_uq"
  // (orgId, defaultReason) WHERE deletedAt IS NULL AND defaultReason IS NOT NULL — у міграції
}
```

`CashOperation` — append-only, не у SYNC_VERSION_MODELS; у audit-whitelist. `ExpenseCategory` — у SYNC.

## Баланс

`balance = initialBalance + Σ(IN.amount) − Σ(OUT.amount)` (SQL-агрегат, `CashService.getBalance`).
Рахується **свіжим поза кешем** (findAll/findOne кешують лише статичну частину каси; balance — завжди актуальний).

## Фіскальна / нефіскальна каса

- **Фіскальна** (`isFiscal=true`): операції з готівкою лише у **відкриту зміну** (`CashShift`); createOperation
  знаходить OPEN-зміну каси або кидає 400. Наявний ПРРО-потік (sellReceipt у зміну) не зачеплено.
- **Нефіскальна**: постійний залишок, операції без зміни (`cashShiftId=null`).

## API Endpoints

**Каси** (`/api/cash-registers`) — OWNER/ADMIN CRUD; список/баланс/історія — +ACCOUNTANT/RECEPTIONIST:

| Метод             | URL                              | Дія                                                                                                  |
| ----------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------- |
| GET               | `/cash-registers`                | Список кас (+ isFiscal/initialBalance/balance)                                                       |
| GET               | `/cash-registers/:id`            | Картка каси (OWNER/ADMIN/ACCOUNTANT)                                                                 |
| POST/PATCH/DELETE | `/cash-registers[/:id]`          | CRUD (OWNER/ADMIN)                                                                                   |
| GET               | `/cash-registers/:id/balance`    | Поточний залишок                                                                                     |
| GET               | `/cash-registers/:id/operations` | Історія (limit, q, dateFrom, dateTo): контрагент / працівник, підстава, номер документа, чек         |
| POST              | `/cash-registers/:id/operations` | Ручна операція за приводом → `CashDeskService.create` (BR-CASH-016…021); `Idempotency-Key` дозволено |

Роль на `POST …/operations`: OWNER/ADMIN/ACCOUNTANT/RECEPTIONIST на рівні маршруту, далі привід звужує
ролі (BR-CASH-021: приймальня — лише «оплата контрагента»).

**Статті руху коштів** (`/api/expense-categories`) — GET OWNER/ADMIN/ACCOUNTANT; CRUD OWNER/ADMIN
(GET/POST/PATCH/DELETE/`:id/restore`/`:id/toggle-active`); `defaultReason` у create/update (409 — привід зайнятий).

Оплати клієнтів і постачальників окремих сторінок не мають: проводяться з каси, з рахунку («Оплатити»
→ `POST /payments`) та із замовлення постачальнику («Оплатити» → `POST /supplier-payments` + `…/confirm`).

## Інтеграції

- **Payments** (`payments.service.create`): оплата клієнта method=cash (`sourceType=CASH_REGISTER`) →
  авто cash-in `reason=SALE_PAYMENT` у **ту саму `$transaction`** що Payment+settlements. Фіскальна каса
  без зміни → 400 → повний відкат оплати.
- **Payroll** (`payroll.service.pay(cashRegisterId?)`): виплата ЗП → cash-out `reason=PAYROLL` по кожному
  співробітнику у `$transaction`. Без каси — лише фіксація `paidAmount` (без руху готівки).

## Інваріанти

1. **Рух готівки лише через `CashService.createOperation`** — append-only, atomic, приймає зовнішній tx.
   Виправлення — сторно-операцією протилежного напряму (не edit/delete).
2. Гроші: `Decimal(12,2)` + `roundMoney`; `amount>0`; знак з `direction`. Баланс не кешується стейл.
3. Tenant-isolation: orgId у кожному запиті; операція валідує касу/статтю/counterparty належать org.
4. Employee ≠ counterparty → ЗП саме касовою операцією (не через SettlementAccount).

→ [docs/objects/payroll.md](payroll.md) · [docs/objects/settlements.md](settlements.md)

## Бізнес-правила (BR-CASH)

> **Зв'язок із банківськими платежами (2026-10-09):** рознесення вихідного платежу як «зняття
> готівки» створює надходження в касу (`MANUAL_IN`, `documentType='BankTransaction'`), а його
> скасування — зворотну видачу (`MANUAL_OUT`). Правила — BR-BANK-034 і BR-BANK-039 у
> `bank-statements.md`; каса тієї самої валюти, що й платіж.

> Правила виведено з коду 2026-10-08, власником не затверджені.

- **BR-CASH-001**: Єдиний писар. Рядок журналу каси (`CashOperation`) створює лише `CashService.createOperation()`. Ніде більше в `apps/api/src` немає запису в `CashOperation` — ні через Prisma-делегат, ні вкладеним записом через `operations: { … }`, ні сирим SQL. Оплата клієнта готівкою, оплата постачальнику готівкою, виплата зарплати з каси й ручні операції йдуть через цей метод
- **BR-CASH-002**: Журнал лише дописується. У коді api немає зміни чи видалення `CashOperation`; у моделі немає `deletedAt` і `updatedAt`. Помилку виправляє зворотна операція протилежного напряму, а не правка рядка
- **BR-CASH-003**: Ізоляція організацій. Каса шукається за `id` + `orgId` серед невидалених (`deletedAt: null`): чужа або видалена каса дає 404 «Касу не знайдено» і в `createOperation`, і в `getBalance`. Стаття шукається так само (`id` + `orgId`, невидалена), відкрита зміна — за `orgId`. Операція пишеться з `orgId` викликача; агрегати залишку (`getBalance`, `getBalances`) та історія (`listOperations`) фільтруються за `orgId`
- **BR-CASH-004**: Сума операції додатна, знак несе `direction`. Сума округлюється до копійки до будь-яких перевірок; якщо після округлення вона не більша за нуль (`0`, від'ємна, менша за пів копійки, `NaN`, `Infinity`) → 400 «Сума має бути додатною», касу не читаємо, нічого не пишемо. У журнал `amount` пишеться додатним і для `IN`, і для `OUT`. Ручна операція із сумою понад місткість колонки `Decimal(12,2)` (9 999 999 999,99, `MONEY_AMOUNT_MAX`) → 400 на рівні схеми, до сервісу не доходить (Bug #846)
- **BR-CASH-005**: Фіскальна каса (`isFiscal = true`) — операція лише у відкриту зміну. `createOperation` шукає невидалену зміну саме цієї каси зі статусом `OPEN`: немає → 400 «Для фіскальної каси відкрийте зміну перед операціями з готівкою», нічого не пишеться; є → її id пишеться в `cashShiftId`. Нефіскальна каса: зміну не шукають, `cashShiftId = null`. Правило діє і на авто-операції (оплата клієнта, оплата постачальнику, зарплата): відмова відкочує всю транзакцію викликача
- **BR-CASH-006**: Каса не йде в мінус. Перед видачею (`OUT`) читається поточний залишок; якщо `залишок − сума` менше нуля (порівняння з допуском −0,001, тож нестача в одну копійку вже блокує) → 400 «Недостатньо готівки в касі: доступно X, потрібно Y», нічого не пишеться. Видати рівно весь залишок можна. Внесення (`IN`) залишком не обмежується. Залишок читається тим самим клієнтом БД, яким пишеться операція, тож кілька видач в одній транзакції (зарплата по співробітниках) бачать уже списане попередніми. Перед читанням залишку видача бере блокування каси на час транзакції (`pg_advisory_xact_lock` за id каси): дві одночасні видачі з однієї каси в РІЗНИХ транзакціях (оплати двом постачальникам) стають у чергу, і друга читає залишок уже з першою
- **BR-CASH-007**: Стаття руху коштів на операції необов'язкова. Якщо задана — мусить існувати в цій організації (інакше 404 «Статтю не знайдено»), бути активною (вимкнена, `isActive = false` → 400 «Стаття вимкнена — оберіть активну») і відповідати напряму: `OUT` — лише стаття типу `EXPENSE` (інакше 400 «Для видачі оберіть статтю витрат»), `IN` — лише `INCOME` (інакше 400 «Для внесення оберіть статтю оприбуткування»)
- **BR-CASH-008**: Ручна операція з причиною `EXPENSE` вимагає статтю: без `expenseCategoryId` → 400 «Для витрати вкажіть статтю витрат», до каси не доходить. Для інших причин стаття необов'язкова. Перевіряє `CashDeskService.create` (`categoryRequired` у `CASH_REASON_RULES`, BR-CASH-016); окремого «ручного» шляху в `CashService` немає — метод `createManual` видалено 2026-10-14, бо обходив правила приводів
- **BR-CASH-009**: Залишок каси = `initialBalance + Σ(IN.amount) − Σ(OUT.amount)` у валюті каси, округлений до копійки. Він щоразу рахується з журналу й окремо ніде не зберігається. Пакетний розрахунок для списку кас (`getBalances`) дає те саме одним запитом; каса без операцій має залишок `initialBalance`. `getBalance` для неіснуючої каси → 404 «Касу не знайдено»
- **BR-CASH-010**: Мультивалюта. Валюта операції — валюта каси (`CashRegister.currencyId`), викликач її не передає. Сума перераховується в базову валюту організації через `ExchangeRatesService.resolveBaseConversion(orgId, валюта каси, зараз, amount)`; у журнал пишуться `amount` (у валюті каси), `amountBase` і `rateUsed`. Якщо конвертація кидає помилку (немає курсу на дату) — вона йде викликачу, нічого не пишеться; тихого відкату на курс 1 немає. Залишок і перевірка «не в мінус» рахуються у валюті каси (`amount`), не в базовій
- **BR-CASH-011**: Атомарність. Якщо викликач передав свою транзакцію (`tx`) — пошук каси, статті, зміни, читання залишку й запис операції йдуть у ній, власна не відкривається (відкат оплати відкочує і рух готівки). Якщо не передав — читання залишку й запис ідуть у власній транзакції рівня `Serializable`; конфлікт серіалізації повертається як 400 «Каса зайнята паралельною операцією — повторіть» в обох формах, у яких він приходить (`P2034` на запиті і `DriverAdapterError` / `TransactionWriteConflict` на COMMIT — `isSerializationConflict`), інші помилки БД не перекладаються
- **BR-CASH-012**: Прив'язка до документа. `reason`, `counterpartyId`, `employeeId`, `documentType`, `documentId`, `notes`, `createdBy` пишуться в рядок журналу як передані, непередані — `null`. `documentType` — довільний рядок (`Payment`, `SupplierPayment`, `PayrollPeriod`), не enum; існування документа, контрагента і співробітника `createOperation` не перевіряє, причину з напрямом не звіряє. Ручна операція: автор — користувач запиту (`CashDeskService` передає `createdBy`)
- **BR-CASH-013**: Аудит. Операція з автором (`createdBy`) залишає в журналі аудиту запис `CREATE` (`CashOperation`, id операції, напрям, сума, причина); без автора — не залишає. Аудит пишеться після запису операції й поза транзакцією: його збій операцію не скасовує і помилки не дає
- **BR-CASH-014**: Ролі. Маршрут ручної операції (`POST /cash-registers/:id/operations`) пускає OWNER, ADMIN, ACCOUNTANT і RECEPTIONIST; які саме приводи кому — уточнює BR-CASH-021 (спершу це були лише OWNER, ADMIN, ACCOUNTANT). Список кас, залишок та історію операцій бачить ще й RECEPTIONIST. Картку однієї каси (`GET /cash-registers/:id`) — OWNER, ADMIN, ACCOUNTANT. Створювати, змінювати й видаляти касу можуть лише OWNER і ADMIN
- **BR-CASH-015**: Історія операцій каси віддається від найновіших до найстаріших, за замовчуванням 100 рядків, не більше 500 за запит (не число, нуль чи від'ємне в `limit` — ті самі 100); зсуву (пагінації) немає. У рядку: суми числами, дата в ISO, назва статті з довідника. Web просить саме стелю (`limit=500`, `CASH_HISTORY_LIMIT`) і, отримавши рівно стільки, пише над таблицею, що старіші операції не вмістились (Bug #849)

> Правила BR-CASH-016…021 — рішення власника 2026-10-14 («каса як місце готівкових оплат»).
> Таблиця приводів — `CASH_REASON_RULES` (`packages/shared/src/schemas/forms/cash-operation.schema.ts`):
> єдине джерело для api, web і тестів.

- **BR-CASH-016**: **Привід визначає напрям і обов'язкові поля ручної операції.** Привід має
  відповідати напряму (внесення / видача) — інакше 400. Привід «зарплата» (`PAYROLL`) ставить
  лише відомість: вручну — 400. Якщо привід вимагає контрагента або працівника, а його не
  вказано, — 400. Контрагент і працівник мають існувати в цій організації й бути не видаленими
  (404). Стаття для приводу «витрата» обов'язкова (BR-CASH-008). (`CashDeskService.create`)
- **BR-CASH-017**: **Оплата контрагента (внесення, `SALE_PAYMENT`).** Обов'язковий контрагент у
  ролі клієнта (`CLIENT` або `BOTH`). Операція створює оплату клієнта через
  `PaymentsService.create` із джерелом «каса»: саме вона зменшує борг, пробиває фіскальний чек,
  нараховує бонуси й пише єдиний рядок каси. Необов'язкова підстава — наряд цього клієнта:
  у статусі «Виставлено» оплата йде за нарядом (наряд може стати «Оплачено»); в іншому статусі
  оплата записується авансом (`PREPAYMENT`), а наряд лишається лише підставою рядка каси.
- **BR-CASH-018**: **Повернення клієнту (видача, `REFUND`).** Обов'язковий контрагент у ролі
  клієнта; необов'язкова підстава — наряд цього клієнта. В одній транзакції: рядок каси і
  транзакція взаєморозрахунків `REFUND_OUT` на ту саму суму (`documentType = 'CashOperation'`,
  `documentId` = id рядка каси). «Сплачено» в рахунку й наряді не змінюється.
- **BR-CASH-019**: **Оплата постачальнику (видача, `SUPPLIER_PAYMENT`) і повернення від
  постачальника (внесення, `SUPPLIER_REFUND_IN`).** Обов'язковий контрагент у ролі постачальника
  (`SUPPLIER` або `BOTH`); необов'язкова підстава — замовлення цього постачальника. Оплата
  створює документ оплати постачальнику й одразу його проводить (`SupplierPaymentsService.create`
  - `confirm`); якщо проведення не вдалося — документ скасовується, каса й борг не змінюються.
    Повернення від постачальника: рядок каси і транзакція `SUPPLIER_PAYMENT_RETURN` (знак −1) в
    одній транзакції; «сплачено» в замовленні не змінюється.
- **BR-CASH-020**: **Документ-підстава** (`baseDocumentType` / `baseDocumentId`) необов'язковий;
  тип — лише той, який дозволяє привід (наряд або замовлення постачальнику), тип і id — разом.
  Підстава має існувати в організації, бути не видаленою й належати контрагентові операції
  (чужа — 400 «Документ-підстава належить іншому контрагентові»). Підстава не те саме, що
  платіжний документ рядка (`documentType` / `documentId`).
- **BR-CASH-021**: **Ролі за приводом.** OWNER, ADMIN, ACCOUNTANT проводять будь-яку ручну
  операцію. RECEPTIONIST — лише «оплату контрагента» (`RECEPTIONIST_CASH_REASONS`); будь-який
  інший привід для нього — 403. Заміняє обмеження BR-CASH-014 щодо ручної операції.
- **BR-CASH-022**: **Привід за замовчуванням у статті руху коштів.** Стаття може мати один
  `defaultReason`; у межах організації привід закріплений щонайбільше за однією невидаленою
  статтею (спроба закріпити вдруге — 409 із назвою статті, що його тримає; у базі — частковий
  унікальний індекс). Напрям приводу має відповідати типу статті (внесення ↔ оприбуткування,
  видача ↔ витрата). Касова операція без указаної статті отримує статтю, за якою закріплено її
  привід, якщо така є й активна, — і ручна, і створена оплатою з рахунку чи замовлення.
  Відновлення видаленої статті, чий привід уже зайнятий, знімає привід із відновленої.

Разом: **491** кейсів (цифри з `vitest --reporter=json`, не з grep). Спільний harness спеків `CashService` — `cash.spec-fixture.ts` (у ньому ж таблиця в пам'яті `memoryTable` для спеків, написаних до коду); harness каси-диригента — `../cash-registers/cash-desk.spec-fixture.ts`.

**Межі сторожів.** Мітка `// guards:` означає «порушення правила в коді валить цей тест» (кожну перевірено мутацією 2026-10-08), але не «правило стережеться повністю»:

- BR-CASH-001, BR-CASH-002 — сторож статичний (читає вихідний код): не бачить запису через змінну-делегат (`const d = tx.cashOperation; d.update(…)`) і вкладеного запису через зв'язок, крім прямого `operations: { … }`. На рівні БД заборони UPDATE/DELETE немає.
- BR-CASH-006, BR-CASH-011 — справжню конкуренцію (два одночасні `OUT` на той самий залишок → другий отримує 400) unit-тест із моком Prisma не відтворює: стережеться лише те, що запитано рівень `Serializable`, обидві форми конфлікту перекладено в 400 і блокування каси взято ДО читання залишку клієнтом транзакції. Наживо перевірено review 2026-10-14 (по 10 раундів із 4 одночасних видач: оплати двом постачальникам, повернення, ручна видача, суміш — рівно одна проходить, каса не йде в мінус, 500 немає). Integration-спеку досі немає.
- BR-CASH-012 — стережеться запис полів «як передані». Те, що існування контрагента, співробітника й документа не перевіряється і що причина не звіряється з напрямом, — відсутність захисту, тестом її не закріплено.
- BR-CASH-014 — ролі перевірено за метаданими `@Roles` контролера. Гейт вкладок і кнопок за роллю на сторінці `/cash` (`page.tsx`, `canOperate`/`canManage`) web-тестом не стережеться.
- BR-CASH-016…022 — тести написано зі специфікації до появи коду (2026-10-14) і мутацією ще НЕ перевірено: яка поломка мусить завалити який кейс — у звіті агента тестів, перевірка — за QA після злиття.
- BR-CASH-017 — стережеться лише те, ЩО каса передає в `PaymentsService.create` (контрагент, сума, джерело «каса», наряд або аванс, «додатки» рядка). Борг, фіскальний чек, бонуси й перехід наряду в «Оплачено» — спеки модуля `payments`. Оплата без підстави: чи це аванс (`PREPAYMENT`), чи звичайна оплата — правило не каже, кейс цього не закріплює.
- BR-CASH-018, BR-CASH-019 (повернення) — «одна транзакція» перевірено фейковим tx-клієнтом: рядок каси й проводка отримали той самий клієнт, а помилка проводки не лишає рядка каси. Справжній відкат у PostgreSQL unit-тест не відтворює. Повтор запиту без `Idempotency-Key` дає другу операцію — тестом не стережеться (запис у `settlements.callers.spec.ts`).
- BR-CASH-019 (оплата) — «каса й борг не змінюються», коли проведення не вдалося, тримає транзакція самого `SupplierPaymentsService.confirm`; тут стережеться лише скасування чернетки й підняття помилки. Випадок «проведення закомітилось, а відповідь упала» (скасування тоді відмовить) не покрито.
- BR-CASH-021 — стережеться сервіс і метадані `@Roles` маршруту. Те, що приймальня бачить на сторінці `/cash` лише «оплату контрагента», — web-тести.
- BR-CASH-022 — частковий унікальний індекс у базі й гонку двох одночасних закріплень unit-тест не відтворює: стережеться перевірка в сервісі й те, що `P2002` індексу стає 409 (update, create) або відновленням без приводу (restore); наявність індексу в базі — `prisma/schema-integrity.integration.spec.ts`. Наживо (review 2026-10-14): два одночасні PATCH з одним приводом — завжди 200 і 409. Виняток із правила: рух власних грошей між банком і касою (`withoutCategory`, BR-BANK-034) статті за приводом не отримує. Привід `PAYROLL` як привід статті правило прямо не дозволяє й не забороняє — кейсу немає. «Стаття за замовчуванням не того типу, що напрям» стережеться м'яко: рядок із такою статтею не пишеться, а чим саме — відмовою чи пропуском статті — правило не каже.
- Кейс `expenseCategoryId не належить org → 404` у `cash.service.spec.ts` мітки НЕ має свідомо: якщо прибрати всю валідацію статті, він лишається зеленим (404 тоді дає пошук каси в `getBalance`). Правило про статтю стереже кейс «стаття не знайдена → 404 «Статтю не знайдено»» у `cash.operation-record.spec.ts`, що звіряє текст помилки.

**Чого тут НЕМА.** Інваріантного спеку (`*.invariants.spec.ts`) немає: властивість «після будь-якої послідовності операцій залишок не від'ємний і дорівнює `initialBalance + ΣIN − ΣOUT`» property-тестом не стережеться.

HTTP-контракт ручної операції покрито з 2026-10-14 (`cash-registers.contract.spec.ts`: нові приводи, підстава, відмови схеми); розбір `?limit=` історії не покриває жоден спек модуля.

Інтеграція з викликачами тут не стережеться: те, що готівкова оплата клієнта, оплата постачальнику й виплата зарплати викликають `createOperation` у своїй транзакції, перевіряють спеки модулів `payments`, `supplier-payments`, `payroll` (їхні дос'є).

Web: `CashPage.test.tsx` — віджет зміни фіскальної каси; `CashOperationModal.test.tsx` — картка операції (поля за приводом, стаття, надсилання, запит перед закриттям з уведеним); `CashOperationsTab.history / .filters / .states.test.tsx` — історія, відбори, межа 500 рядків і помилка списку кас; `lib/__tests__/cache-invalidation.test.ts` — оплата з рахунку й із замовлення скидає кеш каси. Перемикач кас і показ залишку компонентним тестом не покрито.

Каса й оплати поза нею: кеш каси (`cashKeys.all`) скидають і касова операція, і `invalidatePaymentSideEffects` / `invalidatePurchaseSideEffects` (оплата з рахунку, із замовлення постачальнику), і виплата зарплати з каси — інакше залишок і історія лишались старими до 5 хвилин (Bug #848).
