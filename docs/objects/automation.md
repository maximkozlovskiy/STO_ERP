# Automation — правила «подія → умови → дії», розсилки й сповіщення

> Статус: **етап 1, блоки 1–4 реалізовано** (outbox подій; двигун правил, три дії, API правил,
> журналу й дзвіночка, типові правила; власний Telegram-бот — підключення, підписка, опитування,
> канал у правилах; поля згоди контрагента; інтерфейс — розділ «UI (Web)»). Рішення власника
> 2026-10-29 — розділ «Рішення власника».

## Мета

Власник і адміністратор налаштовують без програміста: **коли** (подія документа) → **за яких
умов** (філія, перехід статусу, сума…) → **що зробити** (повідомити клієнта, повідомити
працівників, створити задачу). Приклади власника:

- наряд перейшов у «В роботі» → клієнту SMS / Viber / Telegram «Ваше авто в роботі»;
- наряд «Затверджено» → механіку створюється задача, прив'язана до наряду, і приходить сповіщення
  в системі + SMS / Viber / Telegram.

## Що вже є (дослідження коду 2026-10-29)

- Провайдери: TurboSMS (SMS, Viber), eSputnik (SMS, Viber, Telegram — лише шаблон акаунта, за
  телефоном), SMTP (email). `NotificationChannelConfig` по філії з пріоритетом → ланцюжок
  «Viber → SMS». Черга `sms` (attempts 10, exponential), `NotificationLog`, dead-letter.
- `NotificationTemplate` прив'язаний до закритого enum `NotificationEventType` (11 значень, 6 ніколи
  не надсилаються), `@@unique([orgId, eventType, channel])`, `{{var}}` без каталогу змінних
  (seed-шаблони й payload розходяться).
- EventEmitter2 є; домені події — лише наряд (`work-order.transitioned` {from, to}, `completed`).
  Решта документів подій не генерує. Outbox відкладено (best-effort).
- Дзвіночок у вебі — лише `localStorage`, ніхто не наповнює; бекенду сповіщень немає (блок 4
  замінив його серверним — розділ «UI (Web)»).
- `Task.createdById` обов'язковий — системного автора немає; `Task` пов'язується лише з нарядом,
  авто, контрагентом.
- `Counterparty`: лише `phone`, `email`; `Employee`: `phone`, `email`. Згоди, бажаного каналу,
  Telegram chat id немає.

## Ролі

| Роль                | Що робить                                                                                        |
| ------------------- | ------------------------------------------------------------------------------------------------ |
| OWNER, ADMIN        | Створюють, змінюють, вмикають / вимикають правила й шаблони; бачать журнал; надсилають тест      |
| Будь-який працівник | Отримує сповіщення в системі (дзвіночок) і / або зовнішнім каналом; підписується на Telegram-бот |
| Клієнт              | Отримує повідомлення; може підписатися на Telegram-бот; може відмовитися                         |
| Система             | Ловить подію, перевіряє умови, виконує дії, пише журнал                                          |

## User stories (етап 1)

**US-AUT-1. Правило для клієнта за статусом.**
Як власник, я хочу створити правило «наряд → статус змінено на «В роботі» → повідомити клієнта
Viber, якщо не доставлено — SMS», щоб клієнт знав, що роботу почали, без дзвінка приймальника.

- Given правило увімкнене, у клієнта наряду є телефон і він не відмовився від службових повідомлень
- When наряд переходить у «В роботі» (будь-яким шляхом: кнопка, оплата, автоперехід)
- Then у чергу ставиться одне повідомлення за шаблоном правила з підставленими змінними; у журналі
  — запис зі статусом доставки, документом і правилом.
- Given клієнт без телефону / відмовився → Then повідомлення не створюється, у журналі — «пропущено»
  з причиною.

**US-AUT-2. Задача механіку.**
Як власник, я хочу правило «наряд → «Затверджено» → створити задачу виконавцю наряду «Підготувати
пост і запчастини», термін +2 год, прив'язану до наряду, і сповістити його», щоб механік не
пропустив роботу.

- When наряд стає «Затверджено» → Then створюється задача (виконавець — за стратегією правила,
  автор — системний «Автоматизація», `workOrderId`), механік отримує сповіщення в системі й
  обраним зовнішнім каналом.
- Given у наряду немає призначеного механіка → Then задача — запасному виконавцю з правила; якщо
  його не задано — задачу не створено, у журналі «немає виконавця».

**US-AUT-3. Сповіщення працівникам у системі.**
Як приймальник, я хочу бачити в дзвіночку «Новий онлайн-запис від Іван, 30.10 10:00» з переходом у
документ, щоб не моніторити списки.

- Кожен працівник бачить лише свої сповіщення; лічильник непрочитаних; «позначити прочитаним»,
  «усі прочитані»; клік відкриває документ (`?open=` списку).

**US-AUT-4. Адмінка.**
Як адміністратор, я хочу список правил (назва, подія, дії, увімкнено, останнє спрацювання),
конструктор «подія → умови → дії» з шаблоном і попереднім переглядом, кнопку «Надіслати тест»,
щоб налаштувати розсилки самостійно.

**US-AUT-5. Журнал.**
Як власник, я хочу журнал спрацювань: коли, правило, документ, кому, канал, статус доставки,
помилка — з фільтрами, щоб розібратися, чому клієнт не отримав повідомлення.

**US-AUT-6. Згода й підписки клієнта.**
Як приймальник, я хочу в картці клієнта бачити й змінювати «не надсилати службові», «згода на
маркетинг», бажаний канал і статус Telegram-підписки, а також показати клієнту QR підписки на бот.

**US-AUT-7. Telegram-бот.**
Як власник, я хочу підключити бот СТО (токен у налаштуваннях), щоб працівники й клієнти,
підписані за посиланням, отримували повідомлення безкоштовно й довільним текстом.

## Процес виконання правила

```
Документ змінено (сервіс, у транзакції)        → подія після commit
  ↓ подія {orgId, branchId, documentType, documentId, event, fromStatus, toStatus, actorId}
Диспетчер правил (у процесі API)               → увімкнені правила org для (documentType, event)
  ↓ для кожного: умови (філія, from/to, тип, сума) — якщо ні → кінець (без запису)
  ↓ ключ дедуплікації (rule, document, event, toStatus) — уже був → «пропущено: дубль»
  ↓ дії по черзі:
     ├─ клієнту: одержувач (контрагент документа) → згода/відмова → канали правила або
     │          філії в пріоритеті власника (бот — на своєму місці, лише підписаному; не
     │          підписаний → наступний канал) → шаблон → черга `sms`
     ├─ працівникам: одержувачі (ролі / конкретні / відповідальний з документа) →
     │          сповіщення в системі (БД) + зовнішній канал (бот / SMS) → черга
     └─ задача: виконавець (стратегія) → TasksService.create (автор «Автоматизація») →
                + сповіщення виконавцю
  ↓ журнал: спрацювання + результат кожної дії (у т. ч. «пропущено» з причиною)
Помилка однієї дії не скасовує інших і не скасовує зміни документа.
```

## Бізнес-правила (BR-AUT)

**Правила й події**

- **BR-AUT-001** — Правило: назва, увімкнено, тип документа, подія, умови, ≥ 1 дія, область
  (уся організація або перелік філій). Керують OWNER, ADMIN.
- **BR-AUT-002** — Події етапу 1: `CREATED` і `STATUS_CHANGED` для: наряд, рахунок, замовлення
  постачальнику, складський документ, задача, онлайн-запис; оплата — лише `CREATED` (статусів
  немає); сторно оплати — окрема подія `REVERSED`. Подія виникає **після commit** транзакції і
  **за будь-яким шляхом** зміни статусу (кнопка, автоперехід від оплати, процесор, синхронізація
  з планшета), не лише з кнопки.
- **BR-AUT-003** — Умови етапу 1: зі статусу (будь-який / перелік) → у статус (перелік); філія;
  для наряду — тип ремонту / пріоритет; для рахунку й оплати — сума ≥ X. Усі умови — «І».
- **BR-AUT-004** — Дедуплікація: одне правило на одну подію документа виконується один раз (ключ
  `правило + документ + подія + toStatus + момент зміни`). Повторний перехід у той самий статус
  пізніше (наряд повернули й знову затвердили) — нова подія.
- **BR-AUT-005** — Помилка дії не відкочує зміну документа й не зупиняє інші дії; фіксується в
  журналі.
- **BR-AUT-006** — Вимкнене правило не спрацьовує; зміна правила діє на наступні події, не на
  вже виконані.
- **BR-AUT-007** — Наявні зашиті повідомлення (наряд «Виконано», кошторис, оплата, онлайн-запис,
  нагадування ТО) переводяться в типові правила організації (створюються при міграції / новій
  організації), щоб не було двох паралельних механізмів. Переведення — одразу на етапі 1 (рішення
  власника 2026-10-29): після нього зашиті виклики з сервісів прибираються. Нагадування ТО —
  етап 2 (за часом), до того працює як зараз.

**Повідомлення клієнту**

- **BR-AUT-010** — Одержувач — контрагент документа (наряд, рахунок, оплата, онлайн-запис →
  телефон заявки). Немає контакту для жодного каналу правила → «пропущено: немає контакту».
- **BR-AUT-011** — Канали (рішення власника 2026-10-29: «Я налаштовую самостійно пріоритет, немає
  фіксованих»): правило **без каналів** — «як у налаштуваннях філії»: усі налаштовані канали філії
  в пріоритеті, який задав власник (`NotificationChannelConfig.priority`); перелік каналів у правилі
  (Telegram-бот, Viber, SMS, email, Telegram eSputnik) — явне перевизначення: лише ці канали, у
  цьому порядку. Доставка — перший доступний для клієнта, далі ланцюжок спроб. Типові правила
  каналів не задають. Telegram-бот доступний лише підписаному клієнту. **Бажаний канал клієнта**
  (рішення власника 2026-10-30: «Ставити першим») — у правилі «як у філії», якщо він доступний для
  цього повідомлення (є серед каналів філії, є адреса одержувача; Telegram-бот — клієнт
  підписаний), іде першим, далі решта за пріоритетом філії без повтору; недоступний — просто
  ігнорується (без «пропущено»). Явний перелік каналів правила — перевизначення власника: бажаний
  канал порядку не змінює. Лише для повідомлень клієнту (працівникам — ні); «Надіслати тест» — як
  і раніше, тому, хто тестує.
- **BR-AUT-012** — Тип повідомлення правила: **службове** або **маркетингове**. Службове не
  надсилається клієнту з позначкою «відмовився від повідомлень»; маркетингове — лише зі
  «згодою на маркетинг».
- **BR-AUT-013** — Тихі години (одні на організацію — рішення власника 2026-10-29; типово 21:00–09:00 Києва): повідомлення
  клієнту, що виникло в тихі години, відкладається до їх кінця. Сповіщення працівникам — без
  обмежень.
- **BR-AUT-014** — Текст — лише з шаблону (BR-CFG-004); змінні — з каталогу змінних події (номер,
  статус, клієнт, авто, номер авто, сума, дата / час, філія, телефон філії, посилання на кошторис);
  невідома змінна в шаблоні — помилка збереження, а не порожній текст. **Необов'язковий фрагмент**
  `[[…]]` (Bug #998): якщо хоч одна змінна всередині фрагмента порожня — фрагмент прибирається
  цілком, інакше лишається без дужок: `{{branchName}}[[, тел. {{branchPhone}}]]` без телефону
  організації → «Головна філія». Змінні фрагмента теж лише з каталогу; вкладений `[[`, незакритий
  фрагмент чи `]]` поза фрагментом — помилка збереження (`v.automation.template.fragment`).
- **BR-AUT-015** — Зовнішнє надсилання — лише через чергу з повторами (≥ 10, експоненційно;
  ADR-005); система працює й без інтернету.
- **BR-AUT-016** — Повідомлення правила, що чекає в черзі (відкладене тихими годинами — до ранку),
  на мить відправки має бути ще доречним: документ **видалено** → не надсилається; повідомлення
  про **«створено» оплати** (клієнта / постачальнику), а оплату вже **сторновано** → не
  надсилається; повідомлення про «створено» оплати постачальнику, а її **скасовано** (рішення
  власника 2026-10-30: скасована оплата = сторно, «не надсилати»; так само повернення
  постачальнику — у нього той самий перехід чернетки в «Скасовано») → не надсилається. У журналі —
  «пропущено» з причиною (`DOCUMENT_DELETED` / `PAYMENT_REVERSED` / `DOCUMENT_CANCELLED`).
  Звичайна зміна статусу НЕ скасовує повідомлення (наряд «Виконано» о 23:00, вранці став
  «Оплачено» — «Виконано» лишається правдою); повідомлення про саме сторно чи скасування теж іде.

**Сповіщення працівникам**

- **BR-AUT-020** — Одержувачі: конкретні працівники; ролі; «відповідальний з документа»
  (виконавці наряду, виконавець задачі, автор документа). Звільнені й видалені не отримують.
- **BR-AUT-021** — Сповіщення в системі зберігається в БД per працівник (текст, документ,
  прочитано), видно в дзвіночку; без доступу до документа за роллю перехід недоступний, але
  текст видно.
- **BR-AUT-022** — Зовнішній канал працівнику — Telegram-бот (якщо підписаний) або SMS / Viber за
  телефоном, як обрано в дії.
- **BR-AUT-023** — Ініціатор зміни не отримує сповіщення про власну дію (налаштовується в дії,
  типово так).

**Дія «створити задачу»**

- **BR-AUT-030** — Задача: назва й опис із шаблону, виконавець за стратегією (відповідальний з
  документа / конкретний працівник / роль — найменш завантажений... етап 1: відповідальний або
  конкретний), термін = подія + N годин, пріоритет; прив'язка до документа (наряд — `workOrderId`;
  інші документи — нове поле зв'язку: тип і id документа; з картки задачі — перехід у документ, у
  картці документа — його задачі; рішення власника 2026-10-29).
- **BR-AUT-031** — Автор автозадачі — системний «Автоматизація» (не реальний працівник); у картці
  задачі видно, яке правило її створило.
- **BR-AUT-032** — Повторна подія не створює другу таку саму відкриту задачу для того самого
  документа й правила (BR-AUT-004).

**Telegram-бот і згода**

- **BR-AUT-040** — Токен бота — у налаштуваннях організації (зашифровано); перевірка «Підключити».
- **BR-AUT-041** — Підписка: персональне посилання / QR (одноразовий токен) для клієнта (з картки
  контрагента) і працівника (з профілю); після `/start` бот зберігає chat id і підтверджує;
  `/stop` — відписка.
- **BR-AUT-042** — Поля контрагента: «не надсилати службові», «згода на маркетинг» (дата, хто
  змінив), бажаний канал; зміни — в журналі змін контрагента.

**Журнал і безпека**

- **BR-AUT-050** — Журнал спрацювань: правило, документ, подія, дії з результатом (надіслано /
  пропущено з причиною / помилка), одержувач, канал, провайдер, статус доставки. Доступ —
  OWNER, ADMIN. `NotificationLog` пов'язується з правилом і документом.

  «Додавати вручну»): у режимі «як у філії» бот бере участь лише з рядком, який додав власник, і на
  тому місці, яке він задав.
- До BR-AUT-022: зовнішнє сповіщення працівнику — та сама модель; chat id підписок працівників —
  одним запитом на всю дію.
- До BR-AUT-041, доставка: токен для кроку черги `sms` — з налаштувань організації. Telegram
  відповів 403 («bot was blocked by the user») — усі активні підписки цього чату в організації
  вимикаються, у журналі `REJECTED` з поясненням, ланцюжок іде далі; на мить відправки чат без активної підписки (клієнту — підписки цього контрагента; повідомлення чекало в тихі години, а одержувач надіслав `/stop` чи його відписали) каналу бота не отримує — `FAILED`, ланцюжок далі (Bug #1002; відповіді самого бота — без перевірки); остаточна відмова (4xx, крім 429) на останньому каналі — без повторів черги; 429, 5xx і мережа — повтори (BR-AUT-015).
- До BR-AUT-051: «Надіслати тест» — ще й у Telegram того, хто тестує, якщо він підписаний (каналом
  правила / філії, як звичайне повідомлення); немає ні телефону, ні email, ні підписки — 400.
- До BR-AUT-042: `PATCH /counterparties/:id` (і `POST`) приймає `noServiceMessages`,
  `marketingConsent`, `preferredChannel` (`null` — очистити); зміна згоди на маркетинг — сервер
  ставить `marketingConsentAt` і `marketingConsentById` (той самий стан — без змін); зміни — у
  журналі змін контрагента (аудит `Counterparty`). Картка контрагента й працівника — ще й
  `telegramSubscription: { active, subscribedAt }`. Бажаний канал впливає на порядок каналів
  правила «як у філії» (BR-AUT-011, рішення 2026-10-30).
