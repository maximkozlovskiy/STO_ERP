# CalendarSlot — Dossier

> Слот у календарі підйомника або механіка. Прив'язується до наряду (опціонально) або є незалежним записом.

---

## Prisma модель

```prisma
model CalendarSlot {
  id             String             @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  orgId          String             @db.Uuid
  liftId         String?            @db.Uuid    // підйомник (optional)
  employeeId     String?            @db.Uuid    // механік (optional)
  workOrderId    String?            @db.Uuid    // наряд (optional)
  counterpartyId String?            @db.Uuid    // клієнт без наряду (direct booking)
  vehicleId      String?            @db.Uuid    // авто (optional)
  parentSlotId   String?            @db.Uuid    // split-day continuation (child slot)
  startAt        DateTime
  endAt          DateTime
  status         CalendarSlotStatus @default(BOOKED)  // AVAILABLE | BOOKED | BLOCKED
  type           CalendarSlotType   @default(WORK)    // WORK | MAINTENANCE | BREAK | MEETING
  notes          String?
  syncVersion    BigInt             @default(0)
  createdAt      DateTime           @default(now())
  updatedAt      DateTime           @updatedAt
  deletedAt      DateTime?
}
```

**Відносини:**

- → `Lift` (optional)
- → `WorkOrder` (optional)
- → `Counterparty` (optional — прямий запис клієнта без наряду)
- → `Vehicle` (optional)
- → `CalendarSlot` parent (self-referencing для split-day)
- ← `CalendarSlot[]` continuation (child slots)

**Індекси:**

- `(orgId, startAt, deletedAt)` — range query по даті
- `(orgId, liftId, startAt, endAt)` — конфлікти підйомника
- `(orgId, employeeId, startAt)` — завантаженість механіка
- `(orgId, workOrderId, deletedAt, startAt)` — covering для linked-docs панелі

## Split-day continuation — ключовий інваріант

Слот що перетинає опівніч розбивається на два:

```
parent: startAt=2026-06-14 18:00 → endAt=2026-06-14 20:00  (parentSlotId = null)
child:  startAt=2026-06-15 08:00 → endAt=2026-06-15 11:00  (parentSlotId = parent.id)
```

**Інваріант:** `parent.endAt < child.startAt` (gap = нічний час).

### Зміна запису наряду — через наряд (BR-WO-024)

`PATCH /calendar/slots/:id` (зміна меж у «Дні», форма запису), `sync push calendar_slots` і
`PATCH /by-work-order/:workOrderId` для запису, що належить наряду, не змінюють запис самі:
`WorkOrdersService.updateCalendarSlot` / `moveCalendarByDates` роблять межі ланцюжка запису після
зміни (мін. початок, макс. кінець) плановими датами наряду, підйомник запису — підйомником наряду,
далі — `applyUpdate` → `upsertWorkOrderSlot` (перебудова ланцюжка в транзакції наряду). Зміна лише
примітки чи механіка, запис без наряду й перев'язка до іншого наряду — як раніше, `updateSlot`.
Контролер календаря — у `CalendarApiModule` (імпортує `WorkOrdersModule`), сервіс — у `CalendarModule`.

### Запис наряду — `upsertWorkOrderSlot` (BR-WO-020)

Наряд із плановими початком і завершенням має свій запис; `WorkOrdersService.create/update`
кличуть `CalendarService.upsertWorkOrderSlot(tx, …)` / `removeWorkOrderSlots(tx, …)` у тій самій
транзакції, що й збереження наряду. Проміжок `plannedAt → dueDate` ділиться на робочі години філії
наряду (`splitByWorkHours`, `common/utils/work-hours.ts`): по відрізку на день, перший — якір,
решта — продовження з `parentSlotId` (наряд з 16:00 до завтра 11:00 при 08–18 → 16:00–18:00 і
08:00–11:00). Якір переноситься на місці (id, механік, статус, нотатки зберігаються), продовження
й зайві записи наряду позначаються видаленими й створюються заново. Зайнятість — як у `createSlot`
(свої записи наряду виключено за id, `notIn`, — не `workOrderId: { not }`, який у SQL відкидає
записи без наряду). Робочі години — одне джерело: `workHoursOf` (типові 09–18, як `@default`
BranchSettings і `GET /settings/work-hours`; до 2026-10-16 календар мав власні 08–20).

## Conflict check — обов'язковий при кожній мутації

```typescript
// excludeWorkOrderId — власний WO не є конфліктом з собою
const conflicts = await this.calendarService.checkConflicts({
  liftId,
  startAt,
  endAt,
  excludeWorkOrderId: workOrder.id,
});
if (conflicts.length > 0) throw new ConflictException('Підйомник вже зайнятий');
```

**КРИТИЧНО:** будь-який метод що мутує `startAt/endAt` ОБОВ'ЯЗКОВО викликає conflict probe.  
Пропуск → silent double-booking (Bug #444).

## Бізнес-правила (BR-CAL)

- **BR-CAL-001**: `counterpartyId` може бути заданий прямо (без `workOrderId`) для записів без наряду
- **BR-CAL-002**: `employeeId` — nullable (підйомник без призначеного механіка — теж валідний слот)
- **BR-CAL-003**: `type: MAINTENANCE | BREAK | MEETING` — слот без наряду і без клієнта
- **BR-CAL-004**: «Відкритих» слотів для онлайн-запису немає — вільний час не зберігається, а обчислюється. `BookingService.getAvailability` будує сітку з `BranchSettings` (`workStartTime` / `workEndTime` / `slotDurationMinutes` / `workDays`; без налаштувань — 09:00–18:00, крок 30 хв, пн–пт) і прибирає з неї час, зайнятий на підйомнику БУДЬ-ЯКИМ невидаленим `CalendarSlot` (статус значення не має) і заявками `BookingRequest` зі статусом `CONFIRMED`; вікно доступне, якщо вільний хоч один підйомник філії. Слот без явного статусу створюється як `BOOKED`; підтвердження заявки з обраним підйомником створює новий слот `BOOKED`. Значення `AVAILABLE` в enum `CalendarSlotStatus` існує, і `CreateCalendarSlotDto` його приймає, але ніхто його не створює і не читає (api, web, mobile; у web є лише підпис «Вільний» у `lib/linked-configs.tsx`) — такий слот займає час так само, як `BOOKED`. Справжні «відкриті слоти» — окрема фіча в беклозі
- **BR-CAL-005**: Alternate-mutation endpoint (`PATCH /calendar/slots/by-work-order`, синхронізація з планшета) ОБОВ'ЯЗКОВО повторює conflict probe — з BR-WO-024 обидва йдуть шляхом збереження наряду (`applyUpdate` → `upsertWorkOrderSlot`), тож перевірка зайнятості та сама
- **BR-CAL-006** _(виведено з коду, не затверджено власником)_: слот не може перетинатися в часі з іншим невидаленим слотом тієї самої організації на тому самому підйомнику або в того самого механіка — `createSlot` і `updateSlot` відмовляють 400 (`err.calendar.liftBusy` / `employeeBusy`; для продовження split-day — `liftBusyNextDay` / `employeeBusyNextDay`) і нічого не записують. Перетин напіввідкритий: `startAt < інший.endAt AND endAt > інший.startAt`, тож дотик меж — не конфлікт. Статус і тип іншого слота значення не мають; інший підйомник — не конфлікт; слот без підйомника й механіка ні з чим не конфліктує. `updateSlot` виключає з проби сам слот і перевіряє НОВИЙ підйомник/механіка. Гонку, що обійшла пробу, ловить EXCLUDE `calendar_slots_no_overlap` (лише підйомник) → 409
- **BR-CAL-007** _(з виправлення Bug #819, не затверджено власником)_: на межі робочого дня ділиться лише слот, що ПОЧИНАЄТЬСЯ в робочий час і закінчується після його кінця. Слот, що починається о кінці робочого дня або пізніше (як і той, що починається до відкриття), зберігається одним записом із запитаним часом — без продовження наступного дня. Чи приймати слоти поза робочим часом узагалі — рішення власника
- **BR-CAL-008**: **Вид «Місяць» — лічильники дня за категоріями** (рішення власника 2026-10-15; лише web). Під числом дня — іконка й число для кожної непорожньої категорії, у порядку: «Прострочено» (увесь запис уже закінчився — кінець ЛАНЦЮЖКА багатоденного запису, тобто найбільший `endAt` серед записів із тим самим `parentSlotId ?? id`, < зараз, — а наряд у «Чернетка», «Кошторис», «Погоджено», «В роботі», «Призупинено»; рішення власника 2026-10-15: частина першого дня, що триває продовженням, не прострочена. Продовження на першому дні наступного місяця враховується — місяць довантажує цей день, не показуючи його), «В роботі» (IN_PROGRESS, ON_HOLD), «Заплановано» (ESTIMATE, APPROVED), «Чернетка» (DRAFT), «Виконано» (COMPLETED, INVOICED, PAID, ARCHIVED), «Скасовано» (CANCELLED), «Без наряду» (службовий запис). Запис, що закінчується саме зараз, ще не прострочений; доки поточний час не відомий (до гідратації сторінки), «Прострочено» не ставиться нікому. Продовження багатоденного запису рахується в кожному своєму дні. Загальна кількість записів — у підказці клітинки з правильною множиною («1 запис», «2 записи», «5 записів», «21 запис», «22 записи»); колір завантаженості клітинки лишається. Той самий рядок лічильників — у смузі виду «День» для обраного дня Кожна категорія має СВІЙ колір смуги й іконки — сім різних (рішення власника 2026-10-16: «Чернетка» і «Без наряду» не можуть збігатися, смуга «Скасовано» має бути видна); смуга — контраст не менше 3:1 до фону клітинки чи блоку в обох темах; легенда «?» показує ці кольори. Колір завантаженості клітинки «Місяця» не рахує записів скасованих (`CANCELLED`) і видалених нарядів — так само, як «N год з M» у «Дні» (рішення власника 2026-10-16)
- **BR-CAL-009**: **Вид «Місяць» — картки записів дня** (рішення власника 2026-10-15). Під лічильниками — до 3 карток записів дня за часом початку; решта — посилання «ще N», що відкриває вид «День» на цю дату. Картка: смуга зліва й іконка справа — колір і іконка категорії BR-CAL-008; іконка типу запису (робота / обслуговування / перерва / нарада); час початку; номер наряду й клієнт (механік, який клієнта не отримує, бачить лише номер наряду; запис без наряду — «Без наряду»). Клік по картці відкриває запис у тій самій модалці, що й у виді «День»; минулий запис (за його `endAt`) — лише для перегляду; після збереження чи видалення місяць перечитується. При наведенні на день — дії «Відкрити день» і «Новий запис на цю дату». Кнопка «?» у шапці календаря пояснює іконки й кольори категорій і типи записів
- **BR-CAL-010** _(виведено з `@Roles` контролера, Bug #871; не затверджено власником)_: календар відкривають OWNER, ADMIN, RECEPTIONIST і MECHANIC, а створюють, змінюють і видаляють записи лише OWNER, ADMIN, RECEPTIONIST. Механік бачить запис лише для перегляду (форма «Перегляд слоту» з поясненням, без «Оновити» і «Видалити»); «+ Слот», дії «Новий запис на цю дату», малювання, перетягування й зміна меж запису йому недоступні. Механіку не показуються підказка «Затисніть і перетягніть…» і курсори перетягування та зміни меж блоку (рішення власника 2026-10-16)
- **BR-CAL-011**: **Вид «День» — стан, механік, «зараз», завантаження поста** (рішення власника 2026-10-15). Блок запису — у кольорі категорії BR-CAL-008 (смуга зліва, світлий фон категорії, іконка категорії й іконка типу запису), номер наряду жирним; «прострочено» — за кінцем ланцюжка; блок, що редагується, лишається виділеним; текст на фоні — контраст не менше 4,5:1. На блоці й у підказці — механік запису (прізвище та ім'я; `employeeName` у відповіді `GET /calendar/slots`, і для ролі MECHANIC), якщо призначено; звільнений механік НЕ показується — `employeeName = null` (рішення власника 2026-10-16). Для сьогоднішнього дня (за Києвом) — вертикальна червона лінія поточного часу в межах робочих годин, оновлюється щохвилини; години до неї приглушені; для інших днів і поза робочими годинами лінії немає. Під назвою підйомника — «N год з M»: N — сума тривалостей записів цього підйомника за день у межах робочих годин (запис, що виходить за межі, обрізається; частина багатоденного — лише своя частина дня), M — робочі години дня; N округлюється до 0,5 год, формат «4,5 год з 10». Завантаження поста НЕ рахує записи скасованих (`CANCELLED`) і видалених нарядів (рішення власника 2026-10-16); запис видаленого наряду відповідь `GET /calendar/slots` позначає `workOrderDeleted: true`. Записи видаленого наряду в календарі не показуються НІДЕ — сітка «Дня», картки й лічильники «Місяця», завантаження, колір клітинки (`GET /calendar/slots` їх не повертає; рішення власника 2026-10-16, див. BR-WO-017)
- **BR-CAL-012**: **Механік запису — закріплений за підйомником** (рішення власника 2026-10-16). У формі запису поле «Механік» пропонує лише активних (не звільнених) працівників з роллю MECHANIC, закріплених за підйомником запису (`EmployeeLift`); «— без механіка —» дозволено. Без підйомника («будь-який») поле недоступне з підказкою «Спершу оберіть підйомник»; якщо за підйомником нікого не закріплено — підказка «За підйомником не закріплено механіків». Зміна підйомника скидає механіка, не закріпленого за новим. Збережений механік, якого вже не можна обрати (звільнений чи відкріплений), показується недоступною опцією з поясненням, доки його не змінять; запит без зміни механіка й підйомника його не перевіряє. Сервер: при створенні запису і при зміні механіка чи підйомника `employeeId` має бути активним MECHANIC своєї організації, закріпленим за `liftId` запису (і для продовження багатоденного), інакше 400 «Механік не закріплений за цим підйомником». `GET /employees?liftId=` повертає лише закріплених за підйомником. Рішення власника 2026-10-16: «активний» — не звільнений (FIRED), не видалений і НЕ у відпустці (ON_LEAVE): механік у відпустці не пропонується і не приймається сервером (збережений — недоступна опція). Перетягування чи зміна меж запису у «Дні» на підйомник, за яким механік запису не закріплений, не відхиляється, а знімає механіка (`employeeId: null`) з повідомленням «Механіка знято: не закріплений за підйомником …»; форма запису й далі відповідає 400. Синхронізація з планшета (`sync push calendar_slots`) виконує ту саму перевірку механіка і ролі BR-CAL-010 і відхиляє зміну з причиною. Механік у відпустці має окремий текст (рішення власника 2026-10-16, друге): сервер 400 «Механік у відпустці» (`err.calendar.employeeOnLeave`), тост перетягування «Механіка знято: … у відпустці»; «не закріплений за підйомником» — лише коли справді не закріплений. Запис без підйомника теж отримує точну причину відмови механіка (у відпустці / звільнений чи не механік), а не «не закріплений» (рішення власника 2026-10-16)
- Запис наряду в календарі перетягується разом із нарядом — дати й підйомник наряду змінюються ([work-order.md](work-order.md) BR-WO-023); зміна меж запису, час і підйомник у формі, синхронізація з планшета — теж через дати наряду (BR-WO-024); скасований наряд звільняє свої записи (BR-WO-022).
  Реалізація: у «Дні» перетягування запису з `workOrderId` шле `PATCH /work-orders/:id/reschedule`
  (`slotId`, новий `startAt` перетягнутого запису, `liftId` рядка); сервер зсуває планові дати
  наряду й переносить весь ланцюжок тим самим шляхом, що й збереження наряду; відмова — 400, запис
  лишається на місці з тостом причини. Записи без наряду — `PATCH /calendar/slots/:id`, як раніше.
  Зміна меж (resize) і форма запису наряду поки змінюють сам запис — питання власнику в
  [TECH-DEBT](../TECH-DEBT.md). `GET /calendar/slots` і перевірка зайнятості не бачать записів
  скасованих нарядів; записи нарядів, скасованих до 2026-10-18, вирівняла міграція
  `20261018140000_calendar_slots_of_cancelled_work_orders` (EXCLUDE `calendar_slots_no_overlap`
  бачить кожен живий запис). Прив'язати запис до скасованого наряду (`POST`/`PATCH
/calendar/slots`) — 400 «Наряд скасовано — записати його в календар не можна».

→ [docs/BUSINESS-RULES.md](../BUSINESS-RULES.md) (CalendarSlot split-day invariant)

**Чого тут НЕМА.** Контракт і аспектні спеки є, але стережуть вони не все:

- Conflict probe стережеться лише над сховищем у пам'яті. Справжній перетин проти БД не ганяє ніхто: integration-спек `apps/api/src/prisma/schema-integrity.integration.spec.ts` перевіряє тільки, що EXCLUDE `calendar_slots_no_overlap` ІСНУЄ, а не що він відхиляє пересічні слоти. `syncWorkOrderSlots` перевірено на моках-заготовках (форма `where`), поведінкою — лише конфлікт із записом без наряду (`calendar.conflicts.spec.ts`).
- `checkConflicts()` (read-only проба для UI, `excludeSlotId` / `excludeWorkOrderId`) unit-тестом не стережеться зовсім: контракт-спек мокає сервіс цілком.
- Зайнятість механіка страхує лише app-проба: EXCLUDE-констрейнт покриває підйомник, тож дві одночасні транзакції можуть подвоїти механіка — тестом це не відтворюється.
- Закріплення механіка за підйомником перевіряє лише `CalendarService` (`POST`/`PATCH /calendar`).
  Офлайн-синхронізація (`sync.service.ts`, `PUSH_SAFE.calendar_slots` містить `liftId` і
  `employeeId`) перевіряє тільки, що механік і підйомник належать організації, а не закріплення;
  обмеження ролей календаря вона теж не перевіряє. Перевірка закріплення йде до транзакції запису без блокування: механіка, відкріпленого
  між перевіркою і записом, запис прийме — рішення ревʼю 2026-10-16 як прийнятне, тестом не стережеться.
- Службові типи слота (`MAINTENANCE` / `BREAK` / `MEETING`) перевірені лише як «тип зберігається і слот створюється без наряду й клієнта». Заборони прив'язати до такого слота наряд чи клієнта в коді немає, тож і тесту на неї немає.
- `status` і `type` слота після створення змінити неможливо (`UpdateCalendarSlotDto` їх не містить) — це ніде не зафіксовано тестом.
