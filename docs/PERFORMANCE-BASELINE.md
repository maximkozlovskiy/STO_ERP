### Пастка, що мало не зіпсувала весь вимір

Перші заміри давали **217 мс** на `/api/health` — ендпоїнті, що не торкається БД. Я
спершу пояснив це dev-режимом і source-maps. Перевірка показала інше:

```
curl http://localhost:3000/...   connect=0.213  total=0.219
curl http://127.0.0.1:3000/...   connect=0.0005 total=0.004
```

Уся «затримка» — це резолв `localhost` на Windows (спроба IPv6 → fallback на IPv4),
тобто артефакт клієнта, а не застосунку. **Різниця в 60 разів.** Будь-який замір через
`localhost` на цій платформі безглуздий.

## Що з цього справді можна стверджувати

**N+1 на списках немає — і це висновок, незалежний від обсягу даних.** Час рівний при
зміні `limit` у 100 разів:

```
limit=1    23.7 мс      limit=50   11.0 мс
limit=10   13.7 мс      limit=100  13.0 мс
```

При N+1 `limit=100` коштував би ~у 100 разів більше за `limit=1`. Не коштує — отже
кількість запитів стала, а не пропорційна розміру сторінки. (`limit=1` повільніший за
решту — це перший запит серії, тобто прогрів пулу, не властивість ендпоїнта.)

**Накладні витрати фреймворку малі**: 4 мс на `health` — guard-и, валідація, серіалізація
Fastify. Усе понад це — робота з БД.

**Звіти не є вузьким місцем** на цьому обсязі: 6–10 мс, тобто агрегація вже робиться на
боці БД (`$queryRaw GROUP BY`, `groupBy`, `aggregate`), а не `findMany` + reduce у JS.

## Чого стверджувати НЕ можна

**Ці цифри не прогнозують поведінку на проді.** Найбільша таблиця — 4 795 рядків; на
такому обсязі планувальник обирає seq scan, і якість індексів майже не впливає на час.
Проблема, що проявиться на 100 тис. рядків, тут невидима за визначенням.

Так само нічого не сказано про:

- поведінку під конкурентністю (блокування, вичерпання пулу з'єднань `max: 25`);
- деградацію append-only таблиць (`stock_movements`, `audit_events`) з часом;
- p99 і «довгий хвіст».

## OCR / Excel-імпорт — чисті функції сітки

Виміряно при реалізації локального OCR (плановий етап, 2026-10-02). Збережено тут, бо
при скороченні `MemoryManual.md` 2026-10-05 ці цифри лишились були тільки в історії git,
а вони — єдина підстава рішення «не оптимізувати».

| Функція               | Вхід            | Час        | Джерело       |
| --------------------- | --------------- | ---------- | ------------- |
| `mergeWordsIntoCells` | 3000 фрагментів | **5.8 мс** | user-measured |
| `fragmentsToGrid`     | те саме         | **11 мс**  | user-measured |

**Що з цього випливає.** Обидві — на 3-4 порядки дешевші за сам OCR (`recognize` на
сторінці A4 при 200 DPI = 0.6-1.2 с). Тому оптимізувати їх немає сенсу: виграш
губиться в шумі tesseract. Саме тому їх **не чіпали** під час перф-аудиту.

**Межа твердження.** `user-measured` означає один прогін на машині розробника, не
статистику — для порівняння «що дорожче» цього досить, для абсолютних обіцянок ні.

## Час тестового циклу — повні набори проти селектора (2026-10-07)

Питання: скільки економить `scripts/affected-tests.py` порівняно з «ганяти все».
Одна машина розробника, по одному заміру на рядок — це порядок величин, не статистика.

**Повні набори** (тривалість, яку друкує сам раннер):

| Набір                              | Час      |
| ---------------------------------- | -------- |
| api unit                           | ~15 с    |
| web unit                           | ~66 с    |
| E2E на dev-сервері :3001 (до змін) | ~4 хв    |
| E2E на власному сервері :3002      | 5.4–6 хв |

**Команди селектора** (wall-час, разом зі стартом vitest і E2E-сервера):

| Зміна                                  | Unit | E2E   | Разом |
| -------------------------------------- | ---- | ----- | ----- |
| api `invoices.service.ts`              | 11 с | 154 с | 165 с |
| api `comments.service.ts`              | 14 с | 88 с  | 102 с |
| web `app/(app)/payroll/page.tsx`       | 15 с | 113 с | 128 с |
| web `components/ui/InvoiceCreateModal` | 22 с | 128 с | 149 с |

### Що з цього можна стверджувати

- **Unit-зворотний зв'язок: 11–22 с замість ~80 с** (api + web). Це стійкий виграш.
- **E2E: 1.5–2.5 хв замість 4–6 хв** для локальної зміни. Виграш удвічі-втричі, не на порядок:
  для web-змін додаються 6 наскрізних спеків (a11y, console-errors, smoke…), а для
  api-модуля — сторінки всіх його споживачів.
- **Локальність E2E для api нерівна.** Із 62 модулів із сервісом: у 26 вибір ≤10 спеків,
  у 13 — від 11 до 25, у 23 — понад 25, з них 16 дають «весь suite» (довідники на зразок
  `units`, `warehouses`, `zones`, які використовує майже кожна сторінка). Для 24 сторінок
  web медіана — 7.5 спека, максимум 12.

### Чого стверджувати НЕ можна

- **Що QA-агенти стали швидшими.** Після підключення селектора review ішов ~22 хв, tester —
  ~74 хв, проти ~10 і ~16 хв у попередньому блоці. Але порівнювати нечесно: обсяг інший
  (review переписав селектор, tester робив 20 мутацій із повними прогонами на вимогу).
  Чистого A/B на однаковому diff-і не робили. Час агента визначає обсяг роботи й читання
  скілів, а не тестові команди.
- **Що повний E2E став швидшим.** Він став повільнішим на 1.4–2 хв: Playwright піднімає
  власний сервер із холодною компіляцією і гасить його після прогону. Плата за те, що
  dev-сервер :3001 не чіпається. Теплий E2E-сервер (команда в `docs/GOTCHAS.md`) її знімає —
  не виміряно.

## Наступний крок, якщо потрібні цифри для рішень

Варіант А з обговорення: `docker-compose` (прод-конфіг) + `k6` + засіяні 5–10 тис.
нарядів і 50 тис. рухів складу + окремий профіль throttler-а для тестів. Тоді має сенс
зафіксувати бюджети p95 і додати job у CI поряд із `bundle-budget`.

**Орієнтир навантаження для ADR-001:** система працює офлайн на одному ПК СТО, тобто
реалістичний пік — **10–30 одночасних користувачів** (механіки з планшетів + приймальник),
а не тисячі RPS. Цільові цифри варто ставити від цього, щоб не оптимізувати сценарій,
якого не буде.
