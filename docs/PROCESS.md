# Процес розробки STO ERP — схема

> Одна сторінка про те, **у якому порядку** що відбувається. Правила й обґрунтування —
> у `CLAUDE.md`; робота зі специфікацією — у `/sto-spec`. Тут лише маршрут.

## 1. Спершу — яким маршрутом іти

```
                          ┌──────────────────────┐
                          │   Запит користувача  │
                          └──────────┬───────────┘
                                     │
                    ┌────────────────┴─────────────────┐
                    │ 3+ файли? нова фіча? є вибір між │
                    │ підходами? більше одного кроку?  │
                    └───────┬──────────────────┬───────┘
                        ТАК │                  │ НІ (1–2 файли, баг, текст, доки)
                            ▼                  ▼
                  ┌──────────────────┐   ┌──────────────────────┐
                  │  А. НОВА ЗАДАЧА  │   │  Б. ДООПРАЦЮВАННЯ    │
                  │  (розділ 2)      │   │  (розділ 3)          │
                  └──────────────────┘   └──────────────────────┘
```

Сумнів «дрібне чи ні» → маршрут А.

## 2. Маршрут А — нова задача

```
 ┌─ 0. КОНТЕКСТ ────────────────────────────────────────────────────────────────┐
 │  /sto-context → MemoryManual.md · docs/PHASES.md · активний план             │
 │  dev-сервери: docker (БД+Redis+MinIO) · API :3000 · Web :3001                │
 └──────────────────────────────────┬───────────────────────────────────────────┘
                                    ▼
 ┌─ 1. ПЛАН (план-мод) ─────────────────────────────────────────────────────────┐
 │  EnterPlanMode                                                               │
 │    /sto-analyst  — ЩО: user stories, бізнес-правила BR-{домен}-{N}           │
 │    /sto-spec     — дос'є docs/objects/<entity>.md: правила, зв'язки, аспекти │
 │    /sto-feature  — ЯК: DB / API / UI задачі, файли, аспектні спеки           │
 │  питання користувачу → ExitPlanMode  ◄── БЕЗ ПОГОДЖЕННЯ ДАЛІ НЕ ЙДЕМО        │
 └──────────────────────────────────┬───────────────────────────────────────────┘
                                    ▼
 ┌─ 2. РЕАЛІЗАЦІЯ (план-мод вимкнено) ──────────────────────────────────────────┐
 │  /sto-dev  (стандарти — читається ПЕРЕД кодом)                               │
 │      │                                                                       │
 │      ├─► /sto-database   prisma/schema/*.prisma + міграція                   │
 │      ├─► /sto-backend    DTO · service · controller                          │
 │      │                   + тест у <mod>.<аспект>.spec.ts  (1 аспект = 1 файл)│
 │      └─► /sto-web        сторінка · компонент · хук  → ПЕРЕВІРКА В БРАУЗЕРІ  │
 │                                                                              │
 │  після кожного кроку: правлю аспект → ганяю ОДИН спек-файл з реєстру дос'є   │
 └──────────────────────────────────┬───────────────────────────────────────────┘
                                    ▼
 ┌─ 3. ПЕРЕД КОМІТОМ ───────────────────────────────────────────────────────────┐
 │  unit api + web · type-check · lint      → вердикт лише scripts/verdict.sh   │
 │  гейти специфікацій (check-spec-registry.py):                                │
 │     A  жоден кейс не зник (проти test-baseline.json)                         │
 │     B  немає спека > 900 рядків із ≥2 describe                               │
 │     C  кожен файл із реєстру дос'є існує                                     │
 │  додав/перейменував кейс свідомо → spec-baseline.py, diff у той самий коміт  │
 └──────────────────────────────────┬───────────────────────────────────────────┘
                                    ▼
 ┌─ 4. КОМІТ ───────────────────────────────────────────────────────────────────┐
 │  git commit   (husky: prettier + eslint на staged; --no-verify ЗАБОРОНЕНО)   │
 └──────────────────────────────────┬───────────────────────────────────────────┘
                                    ▼
 ┌─ 5. QA-ЛАНЦЮГ (агенти, строго послідовно) ───────────────────────────────────┐
 │  [бек І фронт] sto-sync-agent ─► sto-review-agent ─► sto-tester-agent        │
 │                                                  [>5 файлів] sto-optimize    │
 │  кожен агент: крок 0 = дос'є агрегату → перевірка → авто-фікс → свій коміт   │
 │  E2E (Playwright) — /sto-e2e, якщо зачеплено UI                              │
 └──────────────────────────────────┬───────────────────────────────────────────┘
                                    ▼
 ┌─ 6. ДОКУМЕНТАЦІЯ ────────────────────────────────────────────────────────────┐
 │  CHANGELOG.md (append) · MemoryManual.md (≤200 рядків, без хешів і цифр)     │
 │  дос'є агрегату: endpoint / поле / FSM / BR / рядок реєстру тестів           │
 │  нова пастка → docs/GOTCHAS.md · новий патерн помилки → скіл sto-dev/review  │
 │  план виконано → перенести в ~/.claude/plans/done/                           │
 └──────────────────────────────────┬───────────────────────────────────────────┘
                                    ▼
 ┌─ 7. ЗВІТ ────────────────────────────────────────────────────────────────────┐
 │  sto-claims-auditor читає ТРАНСКРИПТ і переперевіряє мої твердження          │
 │  Stop-hook блокує відповідь із вердиктом/цифрою без інструмента в цьому ході │
 └──────────────────────────────────────────────────────────────────────────────┘
```

## 3. Маршрут Б — доопрацювання, фікс, баг

```
 ┌─ 1. ЗНАЙТИ, ДЕ ЦЕ ЖИВЕ ──────────────────────────────────────────────────────┐
 │  агрегат → docs/objects/<entity>.md                                          │
 │     «Бізнес-правила (BR-XXX)»          — яке правило зачіпаю                 │
 │     «Аспекти і тести, що їх стережуть» — який спек-файл його стереже         │
 │     «Чого тут НЕМА»                    — чи це відома прогалина              │
 └──────────────────────────────────┬───────────────────────────────────────────┘
                                    ▼
 ┌─ 2. ВІДТВОРИТИ ──────────────────────────────────────────────────────────────┐
 │  баг → спершу тест, що падає, в аспектному файлі (або E2E, якщо це UI)       │
 │  доопрацювання → спершу оновити правило в дос'є, потім тест, потім код       │
 └──────────────────────────────────┬───────────────────────────────────────────┘
                                    ▼
 ┌─ 3. ВИПРАВИТИ ───────────────────────────────────────────────────────────────┐
 │  мінімальна правка → ганяю ОДИН аспектний спек (секунди, не весь набір)      │
 │  UI → перевірка в браузері                                                   │
 └──────────────────────────────────┬───────────────────────────────────────────┘
                                    ▼
 ┌─ 4. ПЕРЕД КОМІТОМ ───────────────────────────────────────────────────────────┐
 │  повний unit зачепленого пакета · type-check · гейти A/B/C                   │
 └──────────────────────────────────┬───────────────────────────────────────────┘
                                    ▼
 ┌─ 5. КОМІТ → QA ЗА РОЗМІРОМ ──────────────────────────────────────────────────┐
 │  1–2 файли, косметика            → лише sto-review-agent                     │
 │  бізнес-логіка (FSM/склад/гроші) → sto-review-agent ─► sto-tester-agent      │
 │  2–3 дрібні фікси можна зібрати й прогнати QA один раз                       │
 └──────────────────────────────────┬───────────────────────────────────────────┘
                                    ▼
 ┌─ 6. ДОКУМЕНТАЦІЯ + ЗВІТ ─────────────────────────────────────────────────────┐
 │  як у маршруті А, кроки 6–7; баг → запис у BUG_REPORT.md                     │
 └──────────────────────────────────────────────────────────────────────────────┘
```

Якщо на кроці 1 з'ясувалося, що зачеплено 3+ файли або треба обирати підхід —
повернутись на маршрут А, крок 1 (план-мод).

## 4. Як специфікація зв'язує код, тест і перевірку

```
   docs/objects/invoice.md                       apps/api/src/modules/invoices/
 ┌────────────────────────────┐               ┌─────────────────────────────────────┐
 │ Бізнес-правила             │               │ invoices.service.ts                 │
 │   BR-INV-001 …             │──── описує ──►│                                     │
 │                            │               │ invoices.due-date.spec.ts           │
 │ Аспекти і тести            │               │ invoices.transition-settlements.…   │
 │   аспект → файл → кейсів   │── вказує на ─►│ invoices.<аспект>.spec.ts           │
 │                            │               │ invoices.spec-fixture.ts (factory)  │
 │ Чого тут НЕМА              │               └──────────────────┬──────────────────┘
 └─────────────┬──────────────┘                                  │ vitest --reporter=json
               │ гейт C: файл існує?                             ▼
               │                              ┌─────────────────────────────────────┐
               └─────────────────────────────►│ scripts/check-spec-registry.py      │
                                              │  A: кейси ⊇ test-baseline.json      │
        apps/api/test-baseline.json ─────────►│  B: розмір спека                    │
        (оновлює лише spec-baseline.py)       │  C: реєстр ↔ диск                   │
                                              └──────────────────┬──────────────────┘
                                                                 ▼
                                                   CI job `quality` · локально перед комітом
```

## 5. Що тримається механічно, а що — на дисципліні

Крок процесу надійний рівно настільки, наскільки його щось примушує.

| Крок                                | Чим тримається                              |
| ----------------------------------- | ------------------------------------------- |
| prettier + eslint на staged         | husky `pre-commit` — механічно              |
| формат commit-повідомлення          | husky `commit-msg` — механічно              |
| unit · type-check · lint            | CI job `quality` — механічно                |
| гейти A/B/C, посилання в доках      | CI job `quality` — механічно                |
| E2E smoke                           | CI job `e2e-smoke` — механічно              |
| вердикт/цифра лише з інструмента    | Stop-hook — механічно (питає «чим виміряв») |
| план-мод перед великою задачею      | правило в `CLAUDE.md` — дисципліна          |
| QA-агенти після коміту              | правило в `CLAUDE.md` — дисципліна          |
| оновлення дос'є, CHANGELOG, GOTCHAS | правило в `CLAUDE.md` — дисципліна          |
| перевірка UI в браузері             | правило в `CLAUDE.md` — дисципліна          |
| ліміт розміру скіла (1500 рядків)   | правило в `CLAUDE.md` — дисципліна          |
| повний E2E                          | вручну (`run_full_e2e` у CI або `/sto-e2e`) |
