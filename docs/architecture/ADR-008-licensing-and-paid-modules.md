# ADR-008: Ліцензування за грейдами користувачів + платні модулі

**Дата:** 2026-06-05
**Статус:** Прийнято
**Автор:** Максим Козловський
**Залежить від:** ADR-001 (offline-first), ADR-005 (черга зовнішніх API), ADR-006 (Cloud Sync Hub)

## Контекст

STO ERP — self-hosted offline-first продукт: клієнт тримає Docker-образи та БД на власному залізі. Потрібна монетизація:

1. **Ліцензії за кількістю користувачів** (грейди), які власник продукту має змогу **сам конфігурувати** (межі, ціни, період, набір модулів).
2. **Платні модулі-сервіси**, що підключаються та оплачуються окремо (напр. хмарні сервіси VIN/крос-коди, хмарний backup, клієнтський портал, розширена аналітика).
3. **Облік ліцензій**: видача дозволів, відстеження підписок, перегляд оплат, автоматичні розсилки.

Ключове обмеження: монетизація **не повинна порушувати офлайн-незалежність** (критичні правила ядра №1–3). СТО мусить працювати без інтернету, навіть якщо ліцензійний сервер недоступний.

## Драйвери рішення

- **Офлайн-незалежність недоторкана** — жодна перевірка ліцензії не зупиняє роботу при відсутності зв'язку.
- **Грейди керовані** власником без зміни коду (config over hardcode, правило №10).
- **Чесна модель захисту**: для on-prem абсолютний захист неможливий (клієнт контролює сервер і БД). Мета — зробити ліцензію **неможливою для підробки** і **невигідною для злому**, а не «невзламною».

## Чесне застереження про захист

Оскільки система працює на залізі клієнта, він має доступ до бази даних і образів. Тому:

- **Запис у БД не є джерелом істини про ліцензію** — його легко змінити. Джерело істини — криптопідписаний токен.
- Локальний код теоретично можна пропатчити. Тому найцінніше прив'язується до хмари (див. «гейтинг сервісів»).
- Остаточний захист — поєднання криптографії, гейтингу онлайн-сервісів та ліцензійної угоди.

## Розглянуті варіанти захисту

### Варіант A: Тільки онлайн-перевірка

Постійна валідація на сервері при кожному вході/дії.
**Вирішальний мінус:** суперечить офлайн-незалежності — при втраті інтернету система стає. Відхилено.

### Варіант B: Тільки офлайн-файл ліцензії

Криптопідписаний файл, жодних «дзвінків додому».
**Плюси:** повна автономність, не підробляється.
**Мінуси:** не видно реальної кількості користувачів і зловживань; складно відкликати/змінити підписку.

### Варіант C: Гібрид (обрано) ✅

Криптопідписана ліцензія + періодична онлайн-активація (heartbeat) з grace-періодом + гейтинг цінних сервісів сервером.
**Плюси:** баланс захисту й офлайн-роботи; видно використання; легко продовжувати/відкликати; підробка неможлива.
**Мінуси:** потребує Cloud Hub і керування ключами.

## Рішення

### 1. Керовані грейди (`LicenseGrade`)

Грейди — конфігуровані записи на Cloud Hub, якими власник керує через адмін-інтерфейс:

```
LicenseGrade
  id, name              // напр. "Free", "Pro", "Business"
  minUsers, maxUsers    // інклюзивний діапазон [min, max]
  priceAmount, currency // ціна в USD (відображення в UAH за курсом НБУ)
  period                // MONTH | YEAR
  includedModuleCodes[] // модулі, що входять у грейд
  isActive, sortOrder
```

**Дефолтний посів** (власник може змінити):

| Грейд      | Користувачів | Ціна            |
| ---------- | ------------ | --------------- |
| Free       | 1–5          | $0              |
| Pro        | 6–10         | $20 / міс       |
| Business   | 11–20        | $50 / міс       |
| Enterprise | 21+          | за домовленістю |

**Усунення перетину меж:** діапазони інклюзивні й суміжні — рівно 5 → Free, 6 → Pro, рівно 10 → Pro, 11 → Business. Система валідує, що грейди не перетинаються і не лишають розривів. Оскільки власник керує сам — UI не дозволяє зберегти грейди з перетином/розривом.

### 2. Ліцензія = криптопідписаний токен (Ed25519)

```
LicenseToken payload:
  orgId, gradeId, maxUsers, enabledModules[],
  issuedAt, expiresAt, hardExpiry, nonce
```

- Hub підписує токен **приватним ключем** (зберігається тільки на Hub).
- ERP має лише **публічний ключ** (вшитий у білд) і перевіряє підпис.
- Клієнт **не може** збільшити `maxUsers`, продовжити термін чи додати модулі — для цього потрібен приватний ключ.
- Токен кешується в `OrganisationSettings` (або окрема модель `LicenseState`).

### 3. Онлайн-активація (heartbeat) з grace-періодом

- ERP раз на `N` днів (напр. 7) надсилає на Hub: `orgId`, `activeUserCount`, версія, підпис інсталяції. **Через BullMQ** (правило №1), ніколи прямим викликом.
- Hub повертає свіжий токен з новим `expiresAt`.
- **Grace:** якщо зв'язку немає, токен дійсний до `hardExpiry` (напр. +30 днів понад `expiresAt`). Робота не зупиняється.
- Якщо heartbeat не проходив понад `hardExpiry` → ERP м'яко відкочується до **Free (1–5)** + банер «потрібна активація», а **не** повне блокування.
- **Захист від підкрученого годинника:** для жорстких перевірок використовується серверний час з heartbeat, а не локальний годинник клієнта.

### 4. Підрахунок користувачів

«Користувач» = активний `Employee`, що має `AuthAccount` (логін), `deletedAt = null`, статус активний.
`LicenseService.assertCanActivateUser()` рахує таких і порівнює з `maxUsers` із токена.

### 5. Enforcement — м'який (обрано)

- **Перевищення ліміту / прострочення підписки** → блокується **тільки створення/активація нового користувача** (`BadRequestException` українською). Наявні користувачі працюють, перегляд і робота не зупиняються.
- **Прострочення оплати модуля** → вимикається **тільки цей модуль**, не вся система.
- Повне блокування системи не застосовується — це зберігає офлайн-роботу й репутацію.

### 6. Платні модулі (`Module`)

```
Module: code, name, description, priceAmount, currency, period
Subscription.modules[] — активні модулі організації
```

- ERP читає `enabledModules` з токена; `ModuleGuard` захищає роути та приховує UI неактивних модулів.
- Приклади: `cloud-services` (VIN/держномер/крос-коди), `cloud-backup`, `client-portal`, `analytics-plus`.
- Модулі — теж конфігуровані власником (ціни, що входить).

### 7. Оплати — український шлюз (обрано)

- Hub інтегрує WayForPay / LiqPay / Fondy (фінальний вибір — на етапі реалізації).
- Підписка → щомісячне автосписання. Webhook успішної оплати → продовження підписки → **перевидача токена** з новим терміном.
- Ціни в конфізі грейда у USD, відображення для клієнта в **UAH за курсом НБУ** (автозавантаження курсу вже реалізовано).
- Моделі `Invoice` + `HubPayment` на Hub. Ручне підтвердження оплати — як запасний варіант.

### 8. Облік, дозволи, розсилки (адмін Hub)

- **Дашборд:** організації, поточні грейди, використання `X / maxUsers`, статуси підписок, прострочення.
- **Дії:** видача/відкликання ліцензії, ручна зміна грейда, продовження, активація модуля.
- **Оплати:** журнал платежів, несплачені рахунки.
- **Розсилки** через `NotificationTemplate` + BullMQ: нагадування про оплату (за 7/3/1 день), квитанції, попередження про наближення до ліміту користувачів і про закінчення підписки, повідомлення про зміну тарифу. Канали: Email / SMS / Viber.

## Модель даних

**На Cloud Hub (нове):**
`HubOrganisation` (акаунт-тенант), `LicenseGrade`, `Module`, `Subscription`, `SubscriptionModule`, `Invoice`, `HubPayment`, `LicenseTokenAudit`, `UsageHeartbeat`, `HubNotificationLog`.

**На локальному ERP (доповнення):**
Поля/модель `LicenseState` (кеш токена, `publicKeyVersion`, `lastActivatedAt`, `graceUntil`), сервіси `LicenseService`, `ActivationProcessor` (BullMQ), guard'и `UsersLimitGuard` та `ModuleGuard`, сторінка `settings/license` (поточний тариф, `X / maxUsers`, активні модулі, термін, статус, кнопка «Активувати»).

## Наслідки

### Позитивні

- Монетизація без шкоди для офлайн-роботи.
- Грейди й модулі керовані власником, без хардкоду (правило №10).
- Підробка ліцензії криптографічно неможлива; злом локального лічильника знецінений гейтингом онлайн-сервісів і оновлень.

### Негативні та їх вирішення

- **Потрібен Cloud Hub** (новий деплой) → реалізується поетапно поверх ADR-006.
- **Керування ключами** → приватний ключ підпису лише на Hub, передбачити ротацію (`publicKeyVersion`).
- **On-prem не дає 100% захисту коду** → приймаємо; доповнюємо ліцензійною угодою, обфускацією та self-integrity перевірками як додатковим бар'єром.

## Тригер перегляду

- Якщо помітна частка клієнтів обходить локальний ліміт → посилити гейтинг сервісів / зменшити інтервал heartbeat.
- Якщо з'явиться потреба в self-service реселерах або міжнародних клієнтах → додати Stripe як другий платіжний провайдер.

## План реалізації (фази)

| Фаза | Зміст                                                                                    |
| ---- | ---------------------------------------------------------------------------------------- |
| L1   | Hub: моделі грейдів / підписок / модулів + керування (CRUD UI з валідацією меж)          |
| L2   | Підпис ліцензій (Ed25519) + видача токена + публічний ключ у ERP                         |
| L3   | ERP: `LicenseService` + `UsersLimitGuard` (м'який) + `ModuleGuard` + сторінка «Ліцензія» |
| L4   | Heartbeat-активація через BullMQ + grace-логіка + захист від підкрученого годинника      |
| L5   | Оплати (український шлюз) + webhooks + автопродовження + `Invoice` / `HubPayment`        |
| L6   | Дашборд обліку + розсилки (нагадування / квитанції / попередження)                       |
