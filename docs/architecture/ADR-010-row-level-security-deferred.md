# ADR-010: Row-Level Security (RLS) — розглянуто, відкладено

**Дата:** 2026-09-17
**Статус:** Прийнято (рішення — НЕ впроваджувати зараз)
**Автор:** Максим Козловський
**Залежить від:** ADR-001 (offline-first), ADR-006 (опційна cloud-sync)
**Пов'язано:** A1 tenant-guard (fail-closed Prisma `$extends` + ALS `runWithTenant`)

## Контекст

Аудит стеку (розділ безпеки, «розглянути») запропонував PostgreSQL Row-Level Security як
**другий рубіж** tenant-ізоляції — щоб навіть баг у застосунку (пропущений `where: { orgId }`)
не міг повернути чужі дані, бо БД сама відфільтрує рядки за політикою.

Поточний рубіж ізоляції вже існує і є **fail-closed**:

- `prisma/tenant-guard.extension.ts` — Prisma `$extends`, який стемпить `orgId` з ambient ALS
  на кожному `create` і кидає `TenantIsolationError`, якщо tenant-контексту немає (окрім явних
  `TENANT_EXEMPT_MODELS` / `runUnscoped`).
- `common/tenant/tenant-context.ts` — `runWithTenant({ orgId })` навколо кожного запиту.
- Ручні `where: { orgId }` у сервісах; guard ловить пропуски.

RLS додав би БД-рівневий бекстоп до цього застосунково-рівневого захисту.

## Драйвери рішення

- **Захищеність:** другий незалежний рубіж (defense-in-depth) проти застосункових багів.
- **Модель розгортання (ADR-001/002):** offline, **один Postgres на інсталяцію СТО**. Setup
  створює одну `Organisation` на базу — де-факто single-tenant-per-install. Кілька орг в одній
  БД трапляються лише у гіпотетичному майбутньому cloud-sync Hub (ADR-006), не на ПК СТО.
- **Офлайн-незалежність:** будь-яка зміна не повинна ускладнити offline `migrate deploy` через
  installer (пастка, що вже одного разу ламала non-root Docker — див. CHANGELOG 136f5d55).
- **Продуктивність:** ПК СТО — скромне залізо; зайвий per-query overhead небажаний.

## Ключові технічні перешкоди (з дослідження коду)

1. **Власник БД оминає RLS.** Застосунок конектиться як `sto` = `POSTGRES_USER` = **власник
   БД**. У Postgres власник таблиці та суперкористувач **BYPASS RLS** за замовчуванням. Щоб RLS
   узагалі спрацював, потрібно або:
   - (а) `ALTER TABLE ... FORCE ROW LEVEL SECURITY` на **кожній** з ~40 orgId-таблиць, або
   - (б) окремий non-owner застосунковий роль (`sto_app`, `NOBYPASSRLS`) з `GRANT`-ами, а `sto`
     лишити тільки для міграцій — **дві ролі, два DATABASE_URL, зміни у compose + installer**.
2. **Session-var + пул з'єднань.** Політика читала б `current_setting('app.org_id')`. Prisma
   тримає **один спільний пул**; звичайні (non-interactive) запити не ділять сесію, тож наївний
   `SET app.org_id` протік би між запитами на переиспользуемом з'єднанні. Коректно — лише
   `SET LOCAL` **усередині транзакції**, тобто обгортати кожен запит у `$transaction` через
   ще один `$extends`-шар → помітний overhead і ризик регресій навколо наявних `$transaction`.
3. **Міграційний ризик.** `ENABLE/FORCE RLS` + політики на всіх таблицях — велика міграція;
   помилка у політиці = **весь застосунок бачить 0 рядків** (fail-closed у найгіршому сенсі),
   причому виявиться лише в рантаймі на інсталяції клієнта.

## Рішення

**НЕ впроваджувати RLS зараз.** Для offline single-tenant-per-install моделі співвідношення
ціна/вигода істотно гірше, ніж у shared cloud multi-tenant БД: реальний ризик (кілька орг в
одній БД) практично відсутній на ПК СТО, а наявний fail-closed app-guard + ALS уже покриває
застосункові пропуски `orgId`. Вартість (окремий роль/FORCE на 40 таблицях, tx-wrap кожного
запиту, installer-зміни, міграційний fail-closed-ризик) не виправдана поточною моделлю.

## Тригер перегляду (коли повертатись до RLS)

Впровадити RLS, якщо/коли настане будь-що з:

1. **Cloud-sync Hub з кількома орг в одній БД** (ADR-006 дозріває до shared-DB multi-tenant) —
   тоді RLS стає першочерговим, а не defense-in-depth.
2. Перехід на **пул-проксі** (PgBouncer) або managed-Postgres із примусовим non-owner ролем.
3. Регуляторна/контрактна вимога БД-рівневої ізоляції орендарів.

При перегляді — обрати варіант (б) «окремий app-роль» (чистіший за FORCE на 40 таблицях) і
реалізувати session-var через tx-scoped `SET LOCAL` у `$extends`-шарі.

## Наслідки

- **Плюси:** нуль ризику регресій/overhead зараз; аудит-пункт закрито обґрунтованим рішенням;
  чіткий тригер і план на майбутнє.
- **Мінуси:** єдиний рубіж tenant-ізоляції лишається застосунковим (guard + ALS). Пом'якшено
  тим, що guard **fail-closed** і покритий інтеграційними тестами (`tenant-guard.integration.spec`).
- **Дія:** підтримувати покриття tenant-guard-тестами; будь-яка нова orgId-модель проходить
  через guard (додається до `TENANT_EXEMPT_MODELS` лише свідомо, як `DeadLetterJob`).
