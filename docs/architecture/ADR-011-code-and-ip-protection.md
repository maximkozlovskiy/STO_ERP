# ADR-011: Захист коду та інтелектуальної власності (self-hosted)

**Дата:** 2026-06-05
**Статус:** Прийнято
**Автор:** Максим Козловський
**Залежить від:** ADR-001 (offline-first), ADR-006 (Cloud Hub), ADR-008 (ліцензування), ADR-009 (оновлення)

## Контекст

STO ERP постачається як self-hosted рішення: клієнт встановлює Docker-образи на власне залізо (ADR-001). Виникає питання — чи захищений код і IP, якщо клієнт сам розгортає систему?

Це рішення фіксує **чесну модель захисту**, межі можливого та конкретні заходи, щоб не мати хибних очікувань.

## Чесне обмеження (фундаментальне)

**Код, який виконується на залізі клієнта, неможливо зробити повністю секретним.** Це стосується будь-якого on-prem софту, не лише нашого.

- Клієнт має образи → `docker save` → розпакування → читання всього вмісту.
- Стек — Node.js/NestJS + Next.js, тобто **JavaScript**: навіть після webpack/мініфікації це не машинний код, а читабельна (деобфускована за бажання) логіка.
- Фронтенд (Next.js static export) повністю віддається в браузер — публічний за визначенням.
- Клієнт має схему БД і дані.

**Ключовий компроміс:** офлайн-незалежність і повна секретність коду — взаємовиключні. Раз ядро мусить працювати без інтернету, воно мусить бути на залізі клієнта, отже доступне йому. Повна секретність можлива лише в SaaS/cloud-only (відхилений Варіант A в ADR-001), що ламає офлайн-роботу.

## Модель загроз

| Хто                          | Доступ                      | Мотив                                    |
| ---------------------------- | --------------------------- | ---------------------------------------- |
| Звичайний власник СТО        | Повний до свого сервера/БД  | Зазвичай немає; ризик випадкового витоку |
| Технічний клієнт / підрядник | Повний до образів і коду    | Обійти ліцензію, скопіювати логіку       |
| Конкурент через клієнта      | Образи, фронтенд-код        | Клонувати продукт, вкрасти алгоритми     |
| Зловмисник у мережі          | Залежить від доступу до LAN | Дані клієнтів, креденшели                |

Що захищаємо за пріоритетом: (1) виручку/ліцензію, (2) секрети й ключі, (3) ключовий IP-алгоритми, (4) загальний код застосунку.

## Розглянуті варіанти

### Варіант A: Cloud-only (повна секретність коду)

Код ніколи не покидає сервер. **Вирішальний мінус:** ламає офлайн-незалежність (ADR-001). Відхилено.

### Варіант B: On-prem без жодного захисту

Просто постачаємо образи. **Мінус:** ні захисту IP, ні виручки. Відхилено.

### Варіант C: On-prem + багатошаровий захист (обрано) ✅

Прийняти межу + тримати секрети й коштовності на Hub + технічні бар'єри + юридичний шар. Захищає те, що реально можна, не порушуючи офлайн-роботу.

## Рішення

### 1. Прийняти межу свідомо

Локальний код не вважається секретним. Захист будуємо там, де він **реально працює**: виручка, секрети, ключовий IP, юридика.

### 2. Секрети — тільки на Hub

Приватний ключ підпису ліцензій, платіжні ключі, хмарні креденшели **ніколи** не потрапляють у клієнтський образ (ADR-008). У клієнта — лише публічний ключ для перевірки.

### 3. Тонкий клієнт + коштовності на Hub (головна стратегія)

Справжній IP — алгоритм підбору крос-кодів, VIN-логіка, цінова аналітика — живе в STO Service як онлайн-сервіс (ADR-006). Локально лишається «звичайний» CRM/наряди/склад: менш цінно красти, а диференціатори фізично недоступні клієнту. Це одночасно захищає IP і підсилює ліцензійну модель.

### 4. Технічні бар'єри (підняти поріг)

- **Ніколи не вантажити source-maps у прод** — інакше це майже вихідний код. Прибрати `.map` з образів.
- Webpack-bundle + мініфікація (вже є у build).
- Опційно для API: компіляція у V8-байткод (`bytenode`) або single-executable (Node SEA).
- Обфускація **лише** кількох чутливих модулів (перевірка ліцензії, integrity), не всього коду.
- Self-integrity перевірки бінарників/бандлів.
- Чітко розуміти: це зупиняє випадкове копіювання, але не цілеспрямованого реверсера.

### 5. Захист виручки й ліцензії (вже в ADR-008)

Криптопідписана ліцензія (підробка неможлива) + гейтинг цінних сервісів/оновлень сервером + heartbeat для виявлення зловживань. Навіть із повним доступом до коду клієнт не відтворить дані й сервіси Hub.

### 6. Юридичний шар (для on-prem — основний)

EULA (ліцензійна угода) + авторське право + умови заборони реверс-інжинірингу й перепродажу. Технічно піднімаємо поріг, юридично — забороняємо.

## Що локально / що на Hub

| Компонент                                  | Локально (ERP)                   | На Hub (Service) |
| ------------------------------------------ | -------------------------------- | ---------------- |
| CRM / наряди / склад / фінанси             | ✅ (прийнятно, що видно)         | —                |
| Приватний ключ підпису                     | ❌ ніколи                        | ✅               |
| Платіжні / хмарні креденшели               | ❌ ніколи                        | ✅               |
| Алгоритм крос-кодів, VIN, цінова аналітика | ❌ (тільки виклик)               | ✅               |
| Перевірка ліцензії                         | ✅ (обфускована, публічний ключ) | ✅ видача        |
| Source-maps                                | ❌ не постачати                  | n/a              |

## Наслідки

### Позитивні

- Виручка, секрети й ключовий IP захищені попри відкритість локального коду.
- Офлайн-незалежність недоторкана.
- Чіткі очікування — без ілюзії «невзламності».

### Негативні та їх вирішення

- **Загальний код застосунку видно** → приймаємо; цінне винесено на Hub, решта захищена юридично.
- **Потрібен EULA** → підготувати до першого комерційного релізу.
- **bytenode/SEA ускладнюють збірку** → застосовувати вибірково (API), не до всього.

### Ризики

- Source-maps випадково потраплять в образ → додати перевірку в CI (fail, якщо `.map` у production-образі).
- Обфускація зламає налагодження → обфускувати тільки чутливі модулі, тримати чисту dev-збірку.

## Тригер перегляду

- Якщо з'явиться доказ масового копіювання локальної логіки → перенести більше функціоналу на Hub (тонший клієнт).
- Якщо клієнти вимагатимуть air-gapped без Hub → переглянути модель захисту IP для таких контрактів окремо.
