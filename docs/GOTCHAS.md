## [2026-10-08] Забутий E2E-сервер `:3002` псується і валить прогін не через код

Сервер, піднятий вручну на `:3002`, після прогону ніхто не зупиняє, а `reuseExistingServer`
підхоплює його наступного разу. Простоявши добу (за цей час диск C: встиг заповнитись до нуля),
екземпляр віддавав 200 на статичні маршрути й 500 на всі `/…/[id]` — «Jest worker encountered
child process exceptions». `webServer.url` перевіряє лише корінь, тож Playwright вважав сервер
здоровим: 24 хв прогону, 23 падіння, 35 незапущених тестів.

Що зроблено: сторож у `apps/web/e2e/setup-auth.ts` перед тестами просить динамічну сторінку й за
5xx зупиняє прогін одразу, з командою для звільнення порту. Перевірено обома боками: проти
заглушки, що віддає 500, прогін зупиняється за 3 с; після зупинки зіпсованого процесу Playwright
сам підняв свіжий сервер і ті самі спеки пройшли. Чистити `.next-e2e` не знадобилось.

Зупиняти треба дерево процесів (`taskkill /PID <pid> /T /F`): `next dev` породжує дочірній
`start-server.js`, і саме він слухає порт.

## [2026-10-08] BullMQ відкидає `add` з jobId активної задачі — self-re-enqueue під тим самим id не працює

Патерн «задача сама ставить наступну з тим самим `jobId`, щоб був single-flight» виглядає
правильно і проходить unit-тести з моком черги. На справжній черзі він не працює взагалі:
`queue.add(name, data, { jobId })` для id, який уже є в Redis, **нічого не додає й не кидає** —
повертає об'єкт задачі, ніби все гаразд. А задача, що зараз виконується, існує до завершення
`process` (навіть із `removeOnComplete: true` її видаляють ПІСЛЯ повернення з обробника).

Так опитування онлайн-оплати виконувалось рівно один раз (Bug #804): виміряно на BullMQ 5.81.4 —
ланцюг із п'яти кроків зупинявся на першому.

```ts
// ❌ зсередини process(): id збігається з id активної задачі — add мовчки відкинуто
await queue.add('poll', next, { jobId: `payment-poll-${intentId}`, delay });

// ✅ новий, але детермінований id на крок: дубль ТОГО САМОГО кроку, як і раніше, зливається
await queue.add('poll', next, { jobId: `payment-poll-${intentId}-p${step}`, delay });
```

Двокрапка в custom jobId заборонена — роздільник дефіс. Перевіряти такий ланцюг можна лише на
живій черзі: `payment-polling.queue.integration.spec.ts` (затримки не чекає — `job.promote()`).
Той самий патерн лишився в `nova-poshta-polling.processor.ts` — не виправлено.

## [2026-10-07] Ліміт у рядках не обмежує розмір; «прочитай файл цілком» може бути нездійсненним

`CLAUDE.md` вимагав: скіл не довший за 1500 рядків. `sto-tester/SKILL.md` мав 1362 рядки —
і 364 КБ: три чверті обсягу лежали в 166 рядках довших за 500 символів (до 2502). Агентові
при цьому наказано «Always start by reading the full skill file», а один `Read` віддає до
25 000 токенів (~39 КБ кирилиці). За транскриптами він читав 5–10% і різав файл `sed`-ом
навмання — тобто більшість чекліста в прогонах участі не брала, і ніхто цього не бачив.

**Правило.** Розмір того, що має бути прочитано, міряти в одиницях читача (КБ / токени), і
перевіряти механічно: `python scripts/check-skill-size.py` (у CI). Інструкцію «прочитай X»
перевіряти по транскрипту виконавця — що він прочитав насправді, а не що йому сказано.

Вимір до і після розкладання — `docs/PERFORMANCE-BASELINE.md`: часу це не зекономило, але
агент тепер читає повні призначені секції замість випадкових шматків.

## [2026-10-07] E2E-сервер :3002 переписує `next-env.d.ts`; `WEB_ORIGIN` перекриває обидва origin-и

Playwright локально ходить на власний екземпляр web (`:3002`, `distDir=.next-e2e`), щоб
не вбивати dev-сервер `:3001`. Два побічні ефекти, які легко прийняти за поломку:

1. **`apps/web/next-env.d.ts` міняється сам.** Кожен `next dev` переписує в ньому шляхи на
   свій `distDir`, тож після E2E там `./.next-e2e/dev/types/...`, після dev — `./.next/...`.
   Файл не комітити у варіанті `.next-e2e`: у CI цієї теки немає. `tsconfig.json` уже
   включає обидві теки, тому локальний `tsc` працює за будь-якого варіанта.
2. **CORS.** API без `WEB_ORIGIN` дозволяє і `:3001`, і `:3002` (`DEV_WEB_ORIGINS` у
   `cors.options.ts`). Якщо `WEB_ORIGIN` заданий в оточенні API — лишається ОДИН origin, і
   весь E2E падає на логіні з `TypeError: Failed to fetch`, не називаючи причини.

Пункт 2 виведено з коду, наживо із заданим `WEB_ORIGIN` не відтворювали. `.env.example`
містить `WEB_ORIGIN=http://localhost:3001` — хто скопіює його як є, отримає саме цю пастку.

Playwright гасить свій сервер після прогону. Тримати його теплим (команда не перевірена
запуском — гілку `reuseExistingServer` на :3002 ще ніхто не проходив):
`cd apps/web && NEXT_PUBLIC_E2E=1 NEXT_DIST_DIR=.next-e2e npx next dev --turbopack -p 3002`.

## [2026-10-07] Локалізація тестів нічого не дає, поки нею ніхто не користується

Спеки api розклали по аспектах і вписали в реєстри дос'є, але жоден крок процесу не питав
«що змінилось → що запускати»: `sto-tester` на кроці 0 і 4 ганяв повний api + повний web,
а повний E2E за один запит ішов 4 рази по ~4 хв. Структура була, виграшу — ні.

Тепер це питання має одну відповідь: `python scripts/affected-tests.py`. Два спостереження,
які змінили задум:

- **Реєстр дос'є для вибору unit не потрібен.** `vitest related <файли>` рахує граф
  імпортів сам і покриває всі модулі api (дос'є є лише в частини), web-тести й залежні
  модулі. Для `invoices.service.ts` це секунди проти повного набору.
- **Хибна локальність гірша за повний прогін.** Файл, який імпортує оболонка всіх сторінок
  (`TopShell` тягне глобальні модалки, а з ними хуки й `components/ui`), чесно дає
  «весь E2E». Скрипт не вгадує: спільний код, конфіги й нерозв'язаний імпорт → ескалація.

## [2026-10-07] Інтеграційний тест на dev-БД: «тестовий» рядок за природним ключем — це чужий рядок

`field-encryption.integration.spec.ts` прибирав за собою через
`DELETE ... WHERE "branchId" = <перша філія> AND channel IN ('SMS','EMAIL')`. Константи звались
`TEST_CHANNEL`/`LEGACY_CHANNEL`, але значення — справжній enum, а `@@unique([branchId, channel])`
гарантує, що на філії такий рядок один. Якщо розробник налаштував SMS, кожен зелений прогін
стирав його конфіг із ключем провайдера (Bug #782).

**Правило.** Тест на спільній БД видаляє лише за `id`, який сам отримав при вставці, або
працює в транзакції, що відкочується. Назва константи `TEST_*` нічого не ізолює — ізолює
значення. Якщо унікальний ключ складається з доменних значень (enum, код, номер), унікального
маркера не вигадати — лишається тільки відкат транзакції:

```ts
await extended.$transaction(async tx => {
  /* seed + перевірки */ throw new RollbackSignal();
});
```

Raw-запити мусять іти через той самий `tx`, інакше вони не бачать незакомічених рядків.

**Як довести.** Вставити пробний рядок із власним маркером, прогнати набір, перевірити, що
рядок на місці. «Набір зелений» цього не показує: він був зелений і тоді, коли стирав.

## [2026-10-07] Оживлений детектор може виявитись генератором хибних спрацювань

Після перенаправлення детекторів на `prisma/schema/*.prisma` цикл «модель без CREATE TABLE»
у `sto-tester` запрацював — і видав 49 `MISSING MIGRATION` на 100 моделей. Причина не в
шляху: `grep -A20 "^model X "` шукав `@@map` у вікні 20 рядків, а `@@map` стоїть у кінці
моделі (`Organisation` — 47 рядків). Доки файл не існував, цього ніхто не бачив.

**Правило.** Полагодив мертвий детектор — запусти його двічі: на поточному коді (очікуваний
вивід відомий?) і на завідомо поганому вході (тимчасова `model ZzFake` без міграції).
«Щось друкує» — ще не «працює».

Той самий клас у `scripts/verdict.sh`: нова гілка Turborepo давала «ЧИСТО» на
`Tasks: 0 successful, 0 total` (нічого не запускалось) і на рядках із префіксом задачі
(`@sto/web:e2e:   15 failed`) — заякорені `^`-патерни падіння їх не бачили, а підсумок
turbo вже вважався ознакою успіху. Нова ознака успіху мусить перевірятись проти ВСІХ
наявних ознак падіння у тому форматі, в якому вони приходять разом із нею.

## [2026-10-07] grep-детектор на неіснуючому файлі мовчки дає «0 проблем»

Схему Prisma давно розбито на 11 файлів (`packages/database/prisma/schema/*.prisma`),
а скіли `sto-review` / `sto-tester` / `sto-optimize` далі ганяли близько 25 детекторів по
`packages/database/prisma/schema.prisma`, якого немає. `grep` на відсутньому файлі пише
помилку в stderr і нічого в stdout — у звіті це виглядало як «порушень не знайдено».

```bash
grep -n "@@unique" packages/database/prisma/schema.prisma      # ❌ exit 2, порожньо
grep -n "@@unique" packages/database/prisma/schema/*.prisma    # ✅ 48 рядків
```

Так само мовчав детектор Bug #220 (`git diff --name-only | grep -q "schema.prisma"`):
ім'я `04_crm.prisma` під шаблон не підпадає, тож «схему змінено без міграції» він би
не побачив ніколи.

**Правило.** Порожній вивід детектора — не доказ чистоти, доки не доведено, що детектор
узагалі здатен спрацювати: перевір, що шлях існує, або дай йому завідомо погане місце.
Перевірка посилань у скілах — `scratchpad`-скрипт цієї сесії показав 11 мертвих шляхів
зі 136; після перейменування файлу/теки шукай старий шлях і в `.claude/`.

## [2026-10-07] Playwright: `if (await el.isVisible({ timeout }))` не чекає

`isVisible()` повертає стан негайно, параметр `timeout` ігнорується. У
`status-tooltip.spec.ts` умова «якщо є поле дати — розширити фільтр» на холодному
рендері давала `false`, фільтр лишався «сьогодні», і тест падав на порожньому списку.
Пройде чи впаде — залежало від того, чи хтось уже створив наряд сьогоднішньою датою.

Заміна: `await el.waitFor({ state: 'visible' })` без `if`. Споріднена пастка —
`a.or(b)` + `toBeVisible()`: коли видно ОБИДВА елементи, strict mode падає
(`counterparty-detail.spec.ts`, flaky). У `e2e/` ще 39 викликів `.or(` — кожен такий
самий кандидат.

Виправлення першого тесту відкрило справжній дефект UI: календар `DatePickerInput`
закривався лише кліком поза ним, тож після введення дати з клавіатури попап лишався
поверх таблиці. Додано закриття на Enter/Escape.

## [2026-10-07] `$(...)` зі шляхом, що містить пробіл, ламає цикл по worktrees

Чистив 40 покинутих agent-worktrees. Перший цикл дав «видалено: 0 | не вдалось: 80» —
80 ітерацій на 40 тек. Причина: шлях `E:/Git/STO ERP/.claude/worktrees/...` містить
пробіл, а `for d in $(git worktree list ...)` ріже його по пробілах на два «шляхи».

```bash
# ❌ 40 тек -> 80 невдалих ітерацій
for d in $(git worktree list --porcelain | grep ^worktree | sed 's/^worktree //'); do ...

# ✅ порядкове читання
git worktree list --porcelain | grep "^worktree " | sed 's/^worktree //' > /tmp/wt.txt
while IFS= read -r d; do ... done < /tmp/wt.txt
```

Корінь проєкту «STO ERP» містить пробіл **завжди**, тож це стосується будь-якого цикла
по шляхах у цьому репо. Той самий клас уже ловився у `.lintstagedrc.js`: там шляхи
обгортають у `JSON.stringify`, бо «просте `files.join(' ')` розривало кожен шлях на два
неіснуючі».

**Друга знахідка того ж прибирання — запобіжник, що спрацював.** Перед видаленням гілок
перевіряв `git rev-list --count main..<branch>`. Перший прохід дав «0 гілок з унікальною
роботою», ПОВТОРНИЙ — знайшов `worktree-agent-a320cff0228e75f48` з 1 комітом
(`1219aea9 fix(review): raw SQL snake_case + tenant safety`, травень). Різниця в тому, що
перший прохід рахував до видалення worktrees, другий — після, і git перестав вважати
гілку «зайнятою» робочою текою.

Коміт був НЕ у main, але його ЗМІСТ перевірено окремо: модуль перейменовано
`settings/document-numbering.service.ts` -> `document-number/document-number.service.ts`,
і фікс там на місці — raw SQL використовує `"includeDate"`, `"currentSeq"` у лапках, плюс
коментар-попередження про camelCase без `@map`. Лише після цього гілку видалено.

**Урок:** «0 унікальних комітів» на одному проході не доводить нічого — перевіряти
повторно після зміни стану, і для кожної знахідки дивитись ЗМІСТ, а не лише наявність
коміту в `main` (файл могли перейменувати).

## [2026-10-07] `field-encryption.integration.spec` залежить від ПОРЯДКУ тестів — ВИПРАВЛЕНО

> **Закрито того ж дня:** рядки тепер створює `beforeEach` (`seedRows()`), кожен тест має
> власну пару. Три прогони з `--sequence.shuffle` проходять. Запис лишено як приклад
> того, як шукати такі залежності.

Знайдено прогоном `vitest run --sequence.shuffle` по всьому api (241 файл) після
розбиття спеків за аспектами. Послідовно — `3118 passed`; з перемішуванням —
`2 failed | 3116 passed`, обидва падіння в одному файлі.

**Файл НЕ пов'язаний із розбиттям:** `git diff 6f47be6e~1 HEAD` по ньому порожній,
тобто дефект передіснуючий, просто його ніхто не шукав.

**Механізм.** Тест `(a)` робить INSERT рядка `notificationChannelConfig`, а `(b)`,
`(d)`, `(e)` його читають. Порядок усередині файлу — неявний контракт:

```
(a) write via extension → ciphertext at-rest   ← створює рядок
(b) read через розширення → PLAINTEXT          ← читає його
(d) update БЕЗ apiKey → ключ збережено         ← падає: Cannot read properties of undefined
(e) lazy re-encrypt                            ← падає так само
```

**Чому це не ловилось.** `dbAvailable` відсікає прогін без БД (`return` у кожному
кейсі), тож на машині без Postgres файл «зелений» і виглядає справним. На машині з
піднятою БД (порт 5432 відкритий) тести виконуються по-справжньому — і тоді порядок
починає мати значення.

**Правильне рішення (не зроблено, свідомо поза обсягом):** кожен кейс створює свій
рядок у `beforeEach`, або сусідні кейси об'єднуються в один. Збільшувати ізоляцію
через `test.sequence` — маскування, а не фікс.

**Урок ширший за цей файл.** `--sequence.shuffle` варто ганяти по ВСЬОМУ набору, не
лише по щойно зміненому модулю: саме так знайшовся дефект у файлі, якого ніхто не
чіпав. Для 8 розбитих модулів shuffle був зелений — тобто розбиття спільного стану
не внесло.

## [2026-10-05] Класифікація grep-ом видає ВИСНОВОК, якого в даних немає

Хотів зрозуміти, який вид тестування реально ловить баги. Прогнав `awk` по
`BUG_REPORT.md` з правилами за ключовими словами і отримав: live 19 / E2E 13 /
static 13 / **unit 0**. Прозвучало як відкриття: «unit-тести не знайшли жодного бага».

**Аудит (`sto-claims-auditor`) показав, що нуль — артефакт класифікатора, не факт:**

1. **Порядок правил.** `unit` перевірявся ОСТАННІМ, після `E2E` (шаблон `spec`) і
   `static` (`review|grep|scan`). Але `*.spec.ts` у цьому проєкті — це **vitest**, тобто
   unit. Кожен такий рядок зараховувався в E2E і до `unit` не доходив ніколи.
2. **Шаблон не ловив латиницю.** `/тест|vitest|unit/` пропускав `test --run`.
3. **Населення непослідовне.** 62 рядки «Виявлено» проти 13 заголовків `## Bug #N` у
   файлі; частина з 62 — підсумки циклів, не окремі баги.
4. **Категорія E2E забруднена:** справді E2E — 4 рядки; решта 9 — `grep` по vitest-спеках,
   тобто статичний аудит прогалин у тестах.

**Контрприклади, перевірені окремо** — баги, знайдені саме прогоном vitest:

- `Виявлено: baseline pnpm --filter @sto/api test --run → 1 failure` (Bug #592);
- подвійний `dispatchEvent` у component-пробі (`NATIVE_POST_COUNT=2`, `expected 2 to be 1`)
  на `SupplierPaymentCreateModal` і `InvoiceCreateModal`.

**Правило.** Класифікація за ключовими словами — **оцінка**, і підпадає під те саме
правило, що й будь-яка цифра (CLAUDE.md, «Вердикт і цифри лише з інструмента»).

**категорія недосяжна за порядком правил**, а не що явища немає. Перед тим як

## [2026-10-05] `\b` у генераторі патча стає БЕЗ-символом — регулярка тихо мертва

Правив регулярки у `check-claims-verified.py` через python-скрипт, що формує новий
текст. У НЕ-raw рядку генератора `"\b"` дало літеральний **backspace** (`\x08`)
замість межі слова. Сталося **двічі** в одному файлі (`RATIO`, потім `DATEISH`).

**Чому не видно жодним звичним способом:**

- `py_compile` — OK, це валідний рядок;
- `grep -n "RATIO"` — показує `\b` (backspace не має видимого представлення);
- редактор — показує так само;
- `cat -A` — ось тут видно: `^H` замість `\b`.

Наслідок: `DATEISH.search("05/10/2026")` → `None`, дата проходила як пропорція і
hook блокував звичайну прозу. Патерн при цьому «виглядав правильним» у кожному
інструменті, крім `cat -A`.

**Діагностика:** `python -c "print(repr(re_obj.pattern))"` — єдина надійна
перевірка. `repr` показує `\x08` явно. Або `grep -c` по `chr(8)` у файлі:

```bash
python -c "import io;print(io.open('файл',encoding='utf-8').read().count(chr(8)))"
# > 0 → у файлі є backspace, майже завжди це зіпсований \x08
```

**Профілактика.** Помилка повторилась ЧЕТВЕРТИЙ раз (2026-10-05, коментар у
`ci.yml`) — усередині `<<'OUTER'`. Тобто перша версія цієї поради була НЕПРАВИЛЬНА:
лапки в heredoc захищають від **shell**, а винуватець інший — не-raw рядок самого
**Python**. `"\\b"` у звичайному рядку дає `\x08`; заміна heredoc'а нічого не
лікує.

Працює лише одне: будувати спецсимвол через `chr(92) + 'b'`, тоді жоден рівень
інтерпретації до нього не дотягнеться. І перевіряти **запуском**, не читанням —
тест `scripts/hooks/test-check-claims.py` ловить усі три поломки цього файлу.

Швидка перевірка після БУДЬ-ЯКОЇ генерованої правки:

```bash
python -c "import io;print(io.open('файл',encoding='utf-8').read().count(chr(8)))"
```

## [2026-10-05] `sys.stdin.read()` у hook декодує cp1251 — кирилиця не матчиться

Stop-hook `scripts/hooks/check-claims-verified.py` шукає у відповіді вердикт
(«чисто», «0 помилок») українськими регулярками. Платформа надсилає payload у
**UTF-8**, але `sys.stdin.read()` декодує **кодуванням консолі**, а в цьому
середовищі воно `cp1251`. Результат: `Усе чисто` ставало `РЈСЃРµ С‡РёСЃС‚Рѕ`.

**Чому пастка підла:** JSON при цьому лишався валідним (мояибаке — теж валідний
рядок), `json.loads` не падав, усі ключі читались, exit code = 0. Hook виглядав
робочим і тихо пропускав **РІВНО ті** відповіді, які мав блокувати. Тест на
англійському тексті цього не ловить.

```python
# ❌ декодує кодуванням консолі (cp1251 на Windows)
raw = sys.stdin.read()

# ✅ байти + явний UTF-8
raw = sys.stdin.buffer.read().decode("utf-8", "replace")
```

**Де ще стосується:** будь-який скрипт, що читає stdin із кирилицею. Для
_виводу_ окремо потрібен `sys.stdout.reconfigure(encoding="utf-8")` — це вже
записано нижче, але то інша половина проблеми: reconfigure на stdout НЕ
виправляє stdin.

**Як перевіряти hook:** payload із кирилицею писати у файл як UTF-8 і подавати
через `< file.json`. Передача через `echo '...' |` у Git Bash дає ще один шар
перекодування і маскує результат.

## [2026-10-04] Nest-опція може мати ІНШИЙ дефолт під Fastify, ніж під Express

`app.enableCors({ origin, credentials, maxAge })` виглядає повним. Під Express так і є —
дефолтний `methods` там повний набір. Під **Fastify** `enableCors` делегує у
`@fastify/cors`, чий дефолт — **лише `GET,HEAD,POST`**:

```
access-control-allow-methods: GET, HEAD, POST     ← DELETE/PATCH/PUT відсутні
```

Браузер мовчки блокує кожен cross-origin `DELETE`/`PATCH`/`PUT` як
`TypeError: Failed to fetch` — без статусу, без тіла, без запису в логах API (запит туди
не доходить). Bug #779.

**Чому це довго не видно:** `supertest`/`curl` **не роблять preflight узагалі** (`curl -X
DELETE` доходив до guard-а і давав чесний 401), а у проді web — той самий origin за Caddy,
тож CORS не застосовується. Проявляється лише cross-origin у браузері.

**Правило:** для кожної Nest-опції, що має платформну реалізацію (`enableCors`,
`useStaticAssets`, body-limit, multipart), задавати значення **явно** й перевіряти
**живим запитом через адаптер**, а не покладатись на дефолт. Типи теж розходяться:
generic `CorsOptions` із `@nestjs/common` ширший за те, чого чекає Fastify-адаптер — тип
краще виводити з сигнатури (`Parameters<NestFastifyApplication['enableCors']>[0]`).

Регресію писати у два рівні: статична перевірка обʼєкта + **живий preflight** через
справжній `NestFactory.create(..., new FastifyAdapter())` — саме другий ловить випадок
«опція задана, але адаптер її проігнорував».

## [2026-10-03] Хелпер-заміна мусить мати контракт НЕ ВУЖЧИЙ за те, що заміняє

`moneyFromDecimal` приймала `{toNumber(): number} | number`. Виглядало правильно —

`TypeError` на значенні, яке попередній код обробляв:

```ts
// raw SQL, ::text-каст, Decimal-подібна обгортка, рядок із зовнішнього API
Number({ toString: () => '350' }); // 350 ✅
moneyFromDecimal({ toString: () => '350' }); // TypeError: value.toNumber is not a function ❌
```

Знайдено падінням 2 payroll-специв; у наборі 14 фікстур мокають Decimal саме як
`{toString}`. **Якби ці шляхи не були покриті тестами, воно впало б у проді.**

Правило: коли вводиш типізовану заміну для вбудованої конверсії (`Number`, `String`,

Там же: NaN не має протікати — `roundMoney` ловить `!isFinite` → 0, інакше NaN пішов би

## [2026-10-03] i18n: захоплене `t` у відкладеному колбеку показує СТАРУ мову

`useTranslation()` повертає `t`, прив'язане до мови на момент рендеру. Якщо колбек має
`deps: []` і виконується **після** зміни мови, він покаже попередню.

Нешкідливо для більшості повідомлень — і критично рівно там, де спливло: `useLanguage`

повідомлення мовою, яку користувач щойно покинув.

```ts
// ❌ deps [] + виконання після зміни мови
const { t } = useTranslation('common');
void apiFetch(...).catch(() => toast.warning(t('language.savedLocallyOnly')));

// ✅ i18n.t читає активну мову В МОМЕНТ виклику
import i18n from '@/i18n/config';
void apiFetch(...).catch(() => toast.warning(i18n.t('common:language.savedLocallyOnly')));
```

`useTranslation` — для рендеру. `i18n.t` — для колбеків, які можуть пережити зміну мови
(також: setTimeout, підписки на події, обробники в ref).

## [2026-10-03] Кодогенерація типів, пастка 3: `interface` у Swagger НЕВИДИМИЙ

Продовження розкатки `openapi-typescript` на 7 модулів. Третій спосіб отримати
«генерація є, а типу немає» — описати вкладену форму як `interface`, а не `class`.

Swagger будує схему з декораторів, а декоратори живуть лише на класах. `interface`
стирається при компіляції — рефлексії нема, схеми нема:

```ts
// ❌ PreviewCandidateDto у документі ВІДСУТНІЙ
export interface PreviewCandidateDto {
  counterpartyId: string;
  counterpartyName: string;
}
// і тому масив доводиться описувати вручну, втрачаючи форму елемента:
@ApiProperty({ type: 'array', items: { type: 'object' } })
candidates!: PreviewCandidateDto[];   // → unknown[] у згенерованих типах

// ✅ клас із @ApiProperty — схема є, $ref проставляється сам
export class PreviewCandidateDto {
  @ApiProperty() counterpartyId!: string;
  @ApiProperty() counterpartyName!: string;
}
@ApiProperty({ type: [PreviewCandidateDto] }) candidates!: PreviewCandidateDto[];
```

**Детектор:** `items: { type: 'object' }` у будь-якому `@ApiProperty` — завжди ознака
втраченої форми. Grep по беку:

```bash
grep -rn "items: { type: 'object' }" apps/api/src --include=*.dto.ts
```

**Межа застосовності патерну (знайдено там само).** Якщо роут приймає `multipart` і
контролер розбирає поля вручну, його DTO у документі не з'являється, хоч би як був
декорований — через нього не проходить жодна валідація Nest. Приклад:
`PreviewImportColumnMapping` у bank-statements (`buildMapping` читає поля з
`file.fields`). Для таких форм рукописний тип у web — правильне рішення, а не борг;
його треба супроводити коментарем, інакше наступний прохід «мігрує» його навмання.

## [2026-10-03] Кодогенерація типів: без `@ApiOkResponse` схеми НЕМА; без swagger-плагіна вона порожня

Крок 4 аудиту (`openapi-typescript`). Дві пастки, через які «генерація є, а типів немає».

**Пастка 1 — анотація відповіді не опційна.** `@ApiOperation({ summary })` описує
операцію, але НЕ її тіло. Без `@ApiOkResponse({ type: X })` у документі лишається
`"200": { "description": "" }`, і `openapi-typescript` згенерує для роута… нічого.
Замір на момент аудиту: лише **23 із 67** контролерів оголошували тип відповіді.
Тому міграція модуля на згенерований тип ЗАВЖДИ починається з анотації його контролера.

```ts
// ❌ тип відповіді у документі відсутній
@Get() @ApiOperation({ summary: 'Список рахунків' }) findAll() {}
// ✅
@Get() @ApiOperation({ summary: 'Список рахунків' }) @ApiOkResponse({ type: PaginatedInvoicesDto }) findAll() {}
```

**Пастка 2 — без swagger CLI-плагіна схема виходить порожньою.** У проєкті 71
рукописний `*ResponseDto`, де поля декоровані БЕЗ явного типу:
`@ApiPropertyOptional() notes?: string | null`. Swagger сам по собі типу не знає
(`emitDecoratorMetadata` для `string | null` дає `Object`), тож у схему потрапляє `{}`,
а `openapi-typescript` чесно перетворює це на **`Record<string, never>`** — тип, у
якого немає жодного корисного поля. Згенеровані типи виглядають «готовими», але
непридатні: `inv.notes` має тип об'єкта, а не рядка.

Лікування — увімкнути `@nestjs/swagger/plugin` (він читає TS-тип з AST) на час емісії.
`nest build` робить це через `nest-cli.json`, а окремий емітер — ні, тож плагін
підключається вручну як TS-трансформер (`apps/api/scripts/compile-for-openapi.js`).
Різниця на цьому проєкті: **173 → 236 схем**, `Record<string, never>` → `string | null`.

**Контроль:** після `pnpm run gen:api-types` перевіряти на конкретному полі, а не
загальним grep-ом — `Record<string, never>` ЗАКОННО лишається для JSON-блобів
(`credentials`, `rawData`, `payload`: у DTO вони `Record<string, unknown>`) і для
boilerplate `webhooks`/`$defs`. Зараз таких 57, і це нормально.

```bash
# має давати `string | null`, а не Record<string, never>
grep -A 25 "InvoiceResponseDto: {" packages/shared/src/api-types.ts | grep "notes"
# кількість схем у документі (плагін увімкнено -> 236; вимкнено -> 173)
node -e "console.log(Object.keys(require('./packages/shared/openapi.json').components.schemas).length)"
```

**Бонус — Nest піднімається без БД і Redis.** `NestFactory.create(AppModule,
new FastifyAdapter(), { preview: true })` будує ПОВНИЙ граф модулів, але не інстанціює
провайдери → `PrismaService.onModuleInit` ($connect) і BullMQ-конекшени не виконуються,
`listen()` не викликається. Саме це робить генерацію сумісною з ADR-001 (офлайн).
`FastifyAdapter` передавати ОБОВ'ЯЗКОВО: без HTTP-драйвера Nest шукає
`@nestjs/platform-express`, якого в проєкті немає, і падає ще до побудови графа.

**Супутня знахідка — один і той самий `documentDate` у двох форматах.**
`InvoiceResponseDto.documentDate` = `YYYY-MM-DD` (`.toISOString().slice(0, 10)`), а
`findByWorkOrder()` для того ж поля віддає повний ISO-datetime (`.toISOString()`).
Видимого бага немає лише тому, що `fmtDate` ковтає обидва. Якщо колись знадобиться
порівняння рядків дат або `.slice(0, 10)` на фронті — зламається.

## [2026-10-02] ExcelJS `writeBuffer()` віддає НЕ node Buffer; `*.spec.ts` роками не типізувались

**Пастка 1 — ExcelJS Buffer.** `exceljs/index.d.ts` оголошує ГЛОБАЛЬНИЙ

```ts
// ❌ бреше: ExcelJS Buffer ≠ node Buffer, у сервісі впаде buffer.toString('utf-8')
const buf = (await wb.xlsx.writeBuffer()) as unknown as Buffer;
// ✅ як у рантаймі (fastify-multipart file.toBuffer())
```

У `types` того конфігу треба перелічувати і @types прод-коду (pdfkit, pdfmake, …) —

**Типові симптоми у специ-помилках і правильна реакція:**

| Помилка                                      | Причина                                                           | Фікс                                                                        |
| -------------------------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------- |

## [2026-10-02] Prisma 6+ резолвить міграції/sql ВІДНОСНО теки схеми — `migrate deploy` тихо не робить нічого

```ts
  schema: path.join('prisma', 'schema'),

});
```

обов'язково в `try/catch`: у CI файлу немає, а `process.loadEnvFile` кидає `ENOENT` і

## [2026-10-02] «Порт 5432 зайнятий svchost» = dockerd мертвий, а не конфлікт портів

**Симптом:** API не стартує з `P1001 Can't reach database server`. На Windows
`Get-NetTCPConnection -LocalPort 5432` показує процес `svchost`; TCP-з'єднання
ВСТАНОВЛЮЄТЬСЯ, але зависає без відповіді. Сирий TCP-тест може навіть «пройти».

**Хибний слід (витратив сесію):** вирішити, що порт захопила стороння служба, або що
WSL після перезавантаження змінив IP і `portproxy` вказує в нікуди. Перевірка IP це
спростовує — адреса та сама.

**Справжня причина:** `svchost` — це `iphlpsvc` (IP Helper), який обслуговує
`netsh portproxy` і СЛУХАЄ порт законно. Він приймає з'єднання і намагається
переслати його у WSL. Але в цьому середовищі немає Docker Desktop і systemd, тож
`dockerd`, запущений через `wsl.exe -e ...`, помирає разом із тією WSL-сесією —
тобто одразу після завершення команди. Portproxy справний, за ним просто нема кого.

**Діагностика в правильному порядку:**

```bash
wsl.exe -e docker ps -q | wc -l   # 0 → демон мертвий; на порти навіть не дивитись
```

**Як підняти стійко** (сесію утримує `sleep`):

```bash
(wsl.exe -u root -e sh -c "dockerd > /var/log/dockerd.log 2>&1 & sleep 3600" &)
sleep 10 && wsl.exe -e docker compose -f docker-compose.dev.yml up -d
```

**Супутня дрібниця:** `pg_isready -U sto` дає хибне «немає відповіді» — база зветься
`sto_erp`. Перевіряти `curl http://localhost:3000/api/health` (database/redis/minio/queue).

## [2026-06-12] Calendar slot continuation колапс при updateMany

`CalendarSlot.parentSlotId` — split-day continuation інваріант: `parent.endAt < child.startAt`. Bulk `updateMany({ workOrderId })` з одним `{startAt, endAt}` колапсує parent+child → data corruption.  
**Правильний патерн:** (1) soft-delete continuations (parentSlotId IS NOT NULL); (2) update тільки parent (parentSlotId IS NULL); (3) recreate child якщо range перевищує день.
