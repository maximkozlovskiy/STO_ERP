# Інструкція для Claude Code: реструктуризація документації STO ERP

> **Кому:** Claude Code, що працює над репозиторієм STO ERP.
> **Що зробити:** розбити роздутий `MemoryManual.md` (2994 рядки / ~512 КБ) на чисту трирівневу структуру документації **без втрати жодного факту**.
> **Режим:** це не нова фіча коду — план-мод не обов'язковий, але працюй акуратно і роби бекап перед переміщенням.

---

## 1. Навіщо це робиться (контекст)

Зараз `MemoryManual.md` змішує три різні типи інформації, які мають жити окремо:

1. **Довговічний довідник** (архітектура, патерни, бізнес-правила, моделі) — змінюється рідко.
2. **Журнал по комітах** (десятки записів `UI:`, `Pricing:`, `Fix:`, `Perf:`, `Gotcha:` з хешами) — росте з кожним комітом, це ~80% обсягу.
3. **Поточний стан проєкту** — дублюється **тричі** (рядки ~1328, ~1735, ~2252).

Файл читається **на старті кожної сесії і щогодини в loop** (див. `CLAUDE.md`). 512 КБ старого журналу палять бюджет контексту даремно.

**Ціль:** `MemoryManual.md` має лишитись тонким (≤200 рядків) знімком поточного стану з посиланнями. Решта — у спеціалізованих файлах.

---

## 2. Цільова структура

```
STO/
├── MemoryManual.md            ← ТОНКИЙ: останній commit + поточний стан + посилання (≤200 рядків)
├── CHANGELOG.md               ← весь журнал по комітах (append-only)
├── CLAUDE.md                  ← оновити посилання на нову структуру
├── PHASES.md                  ← лишити де є (root)
├── docs/
│   ├── ARCHITECTURE.md        ← де що живе, API модулі, Prisma моделі, sync
│   ├── PATTERNS.md            ← Universal/UI Patterns, Design System, EntityPicker, ModalTabs тощо
│   ├── BUSINESS-RULES.md      ← критичні бізнес-правила, FSM, інвентар, розрахунки
│   ├── GOTCHAS.md             ← відомі пастки (накопичується окремо)
│   ├── specs/
│   │   └── _TEMPLATE.md       ← шаблон специфікації нової фічі
│   └── objects/
│       ├── _TEMPLATE.md       ← шаблон досьє доменного об'єкта
│       └── work-order.md      ← приклад: повне досьє «Наряд» (vertical slice)
```

### Три рівні документації (принцип)

- **Горизонтальні довідники** (`ARCHITECTURE.md`, `PATTERNS.md`, `BUSINESS-RULES.md`, `GOTCHAS.md`) — спільне, **одне місце правди**.
- **Вертикальні досьє** (`docs/objects/<entity>.md`) — все про один об'єкт (UX/UA + архітектура + бек) з **посиланнями** на горизонтальні, без копіювання спільного.
- **Specs** (`docs/specs/`) — контракт _нової_ фічі (тимчасовий, «ЩО будуємо»). Після релізу суть осідає у відповідне досьє.

---

## 3. Залізні правила (дотримуйся під час усієї роботи)

1. **Жодного втраченого факту.** Кожен рядок змісту з `MemoryManual.md` має опинитись у новому файлі. Це переміщення/реорганізація, не видалення інформації.
2. **Дедуплікація — лише ідентичного.** Якщо два записи дублюють один факт (3× «Поточний стан», 2× pricing-запис) — лиши один найповніший, решту прибери.
3. **Не копіюй спільне в досьє.** У досьє об'єкта пиши тільки специфічне для нього, а спільні патерни/дизайн-систему давай **посиланням** на `docs/PATTERNS.md`.
4. **Бекап перед стартом.** Скопіюй оригінал у `MemoryManual.backup.md` (або зроби git-коміт «before docs restructure»), щоб був відкат.
5. **Записи з хешем комітів** → у `CHANGELOG.md`. Якщо запис описує і _патерн_, і _коміт_ — витягни багаторазовий патерн у `PATTERNS.md` (без хеш-шуму), а в `CHANGELOG.md` лиши один датований рядок з посиланням.
6. **Українська мова** збереженого тексту лишається українською.

## 4. Покрокова інструкція

### Крок 0 — підготовка

- Прочитай повністю `MemoryManual.md`.
- Зроби бекап (`MemoryManual.backup.md` або git-коміт).
- Створи теки `docs/`, `docs/specs/`, `docs/objects/`.

### Крок 1 — горизонтальні довідники

Перенеси розділи за цим мапуванням (орієнтовні поточні заголовки/рядки — звіряй за змістом, не лише за номером):

**→ `docs/ARCHITECTURE.md`**

- «Архітектура — де що живе»
- «Всі API модулі (28)»
- «Prisma — всі 41 моделей»
- «Синхронізація (`sync.service.ts`)»

**→ `docs/PATTERNS.md`**

- «Universal Patterns (B1-B7 + C)»
- «UI Patterns»
- «Design System (Tailwind 4)»
- «EntityPickerField + \*EditModal стандарт»
- «sto-dev §14 — Modal+ModalTabs паттерн»
- багаторазові UI-патерни з журналу: ModalTabs, `useDirtyForm`, detail panel (`useDetailPanelConfig`), `useTableColumns`, AnimatedBody, ConfirmDialog+`useConfirm`, збережені фільтри / групові дії / захист змін
  → витягни як **патерн** (опис + приклад використання), без прив'язки до конкретного хеша.

**→ `docs/BUSINESS-RULES.md`**

- «Критичні бізнес-правила (завжди пам'ятати)»
- FSM нарядів, правила інвентаря, правила розрахунків (settlements)

**→ `docs/GOTCHAS.md`**

- «Відомі пастки (gotchas)»
- «Gotcha — UpdateCounterpartyDto не має поля type» та інші точкові gotcha-записи

### Крок 2 — дедуплікація

- Об'єднай три секції «Поточний стан проєкту» в **одну** найактуальнішу (вона піде у тонкий `MemoryManual.md`, Крок 4).
- Об'єднай дублікати pricing-записів («розцінка по PO і по списку XLSX/CSV», що повторюються) в один.

### Крок 3 — `CHANGELOG.md`

- Перенеси сюди **всі** записи по комітах: `Perf:`, `Pricing:`, `Fix:`, датовані `UI: ... (хеш)`, «Фаза 16 прогрес», «Архітектура змін Фаза 16», розділ «Changelog (останні коміти)».
- Формат: зворотній хронологічний порядок, заголовок = `## <дата> — <короткий опис> (<хеш>)`.
- append-only; старі фази можна згодом виносити в `docs/changelog-archive/`, але зараз просто збери все в один файл.

### Крок 4 — тонкий `MemoryManual.md`

Має містити ТІЛЬКИ:

- `## Останній commit` (актуальні хеші, статус TypeScript/тестів)
- `## Поточний стан проєкту` (одна об'єднана версія з Кроку 2)
- `## Карта документації` — список посилань:
  - Архітектура → `docs/ARCHITECTURE.md`
  - Патерни / Design System → `docs/PATTERNS.md`
  - Бізнес-правила → `docs/BUSINESS-RULES.md`
  - Пастки → `docs/GOTCHAS.md`
  - Журнал змін → `CHANGELOG.md`
  - Досьє об'єктів → `docs/objects/`
  - Специфікації фіч → `docs/specs/`
  - Фази → `PHASES.md`
- Ціль: **≤200 рядків**.

### Крок 5 — досьє об'єктів (vertical slice)

- Створи `docs/objects/_TEMPLATE.md` (структура нижче, §5).
- Створи **одне реальне досьє-приклад** `docs/objects/work-order.md` («Наряд»), зібравши FSM / Prisma-модель / endpoints / DTO / UI з наявних файлів (`MemoryManual.md`, `BUSINESS-RULES.md`, схеми, api/).
- **Не** створюй досьє на всі 41 модель. Лише список-заготовки (порожні файли або секція «TODO») для ключових агрегатів: **Наряд, Контрагент, Товар/Інвентар, Розрахунки, Запис/Календар**. Дрібні сутності лишаються полями цих агрегатів.

### Крок 6 — шаблон специфікації

- Створи `docs/specs/_TEMPLATE.md` (структура нижче, §6).

### Крок 7 — оновити `CLAUDE.md`

- У секціях «Відновлення після ліміту / нова сесія» і «Щогодинний моніторинг (loop)»: вкажи, що `MemoryManual.md` тепер тонкий, а деталі — у `docs/*`.
- У правилі «Оновлення MemoryManual (після кожного коміту)»: додай, що тепер:
  - новий запис по коміту → `CHANGELOG.md` (не `MemoryManual.md`);
  - новий багаторазовий патерн → `docs/PATTERNS.md`;
  - нова/змінена бізнес-логіка → `docs/BUSINESS-RULES.md`;
  - зачеплений доменний об'єкт → оновити його `docs/objects/<entity>.md`;
  - `MemoryManual.md` оновлюється тільки в частині «Останній commit» + «Поточний стан».
- Звір шляхи: переконайся, що посилання на `PHASES.md` у `CLAUDE.md` збігаються з реальним розташуванням (зараз `PHASES.md` у корені — або лиши в корені, або перенеси в `docs/` і онови **всі** посилання консистентно).

### Крок 8 — верифікація (обов'язково)

- Перевір, що **жоден факт не зник**: порівняй заголовки/ключові пункти оригіналу (з бекапа) зі вмістом нових файлів. Можна grep-ом по ключових термінах (`FSM`, `InventoryService`, `createMovement`, `EntityPicker`, `ModalTabs`, назви моделей).
- Перевір, що в `MemoryManual.md` не лишилось журнальних записів з хешами.
- Перевір, що немає трьох «Поточний стан».
- Перевір, що всі посилання в «Карта документації» ведуть на існуючі файли.
- Виведи короткий звіт: скільки рядків було / стало в `MemoryManual.md`, які файли створено, що куди перенесено.
- Зроби git-коміт: `docs: restructure MemoryManual into layered docs (architecture/patterns/business-rules/changelog + object dossiers)`.

## 5. Шаблон досьє об'єкта — `docs/objects/_TEMPLATE.md`

```markdown
# Об'єкт: <Назва UA> (<EntityName>)

## Призначення / бізнес-зміст

Що це за сутність і навіщо вона в системі.

## Бізнес-правила та FSM

- transition map статусів (хто, коли, за яких умов)
- інваріанти (напр. зміна залишків тільки через InventoryService.createMovement())
- посилання на спільні правила: див. docs/BUSINESS-RULES.md

## Дані (Prisma)

- модель <EntityName>, ключові поля, звʼязки
- обов'язкові поля: orgId, createdAt, updatedAt, deletedAt, syncVersion

## API

- endpoints (метод + шлях)
- DTO
- сервіс-методи (напр. transition(), createTransaction())

## UI / UX (UA)

- сторінки / модалки, де фігурує об'єкт
- компоненти (EntityPicker, ModalTabs, колонки) — деталі патернів див. docs/PATTERNS.md
- тексти/валідація українською

## Edge cases

офлайн (черга з retry), soft-delete (deletedAt), tenant isolation (orgId)

## Посилання

- spec фіч: docs/specs/...
- ADR: ...
- останні зміни: CHANGELOG.md
```

## 6. Шаблон специфікації — `docs/specs/_TEMPLATE.md`

## 7. Чого НЕ робити

- ❌ Не видаляй інформацію «бо застаріла» — переноси в `CHANGELOG.md`, рішення про архів прийме людина.
- ❌ Не створюй досьє на всі 41 модель — лише ключові агрегати.
- ❌ Не копіюй Design System / спільні патерни в кожне досьє — тільки посилання.
- ❌ Не залишай журнальні записи з хешами в `MemoryManual.md`.
- ❌ Не починай без бекапа.

## 8. Критерій «готово»

- [ ] `MemoryManual.md` ≤200 рядків, лише поточний стан + посилання.
- [ ] Створено `docs/ARCHITECTURE.md`, `docs/PATTERNS.md`, `docs/BUSINESS-RULES.md`, `docs/GOTCHAS.md`, `CHANGELOG.md`.
- [ ] Створено `docs/specs/_TEMPLATE.md`, `docs/objects/_TEMPLATE.md`, `docs/objects/work-order.md`.
- [ ] Жоден факт не втрачено (звірено з бекапом).
- [ ] Дублікати усунено (1× «Поточний стан», 1× pricing).
- [ ] `CLAUDE.md` оновлено під нову структуру.
- [ ] Зроблено git-коміт зі звітом про перенесення.
